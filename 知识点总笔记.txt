============================================================
一、项目全景：分层架构
============================================================

【一句话】每层只干一件事，依赖箭头只能向下。

  用户（浏览器 / curl / Postman）
        |
        v
  界面层  OrderController.java（HTTP 接口）
        |        只负责：读输入、显示结果；不做任何业务判断
        v
  业务层  OrderService.java
        |        只负责：业务规则（订单号不重复、金额>0、状态流转）
        v
  数据层  OrderRepository.java
        |        只负责：订单怎么存、怎么取（Map -> 数据库）
        v
  实体    Order.java（一笔订单长什么样）
          OrderStatus.java（状态只能有哪几种取值）

【各文件职责】
  OrderStatus.java ... 枚举，定义状态取值：UNPAID / PAID / CANCELLED
  Order.java ......... 实体，3 个字段 + 构造方法 + getter + setStatus + toString
  OrderRepository.java 数据层，add / updateStatusIfUnpaid / get / listAll / listPage / contains / count
  OrderService.java .. 业务层，createOrder / findOrder / listOrders / pay / cancel / sumAmount
  OrderAppApplication.java  程序入口，@SpringBootApplication
  OrderController.java  接口层，把 HTTP 请求翻译成 service 调用
  ApiExceptionHandler.java  全局异常处理，所有异常 -> 统一 JSON 格式
  dto/ ............... 对外数据结构：CreateOrderRequest / OrderResponse / PageResponse
  （早期的控制台入口 Main.java 已在项目转为 Web 服务后删除）

【最核心的一句话】
  OrderController 里【一个业务判断都没有】。
  规则全在 OrderService —— 改规则只动一个文件。
  这就是为什么不用把代码全塞进一个文件里。

【分层的回报（实测）】
  把 Map 换成 H2 数据库时，只改了 OrderRepository（+pay/cancel 写回一句），
  Main、OrderController、OrderStatus、Order 都没动。


============================================================
二、Java 基础知识点
============================================================

【2.1 枚举 enum】
  public enum OrderStatus { UNPAID, PAID, CANCELLED }

  为什么不用字符串 "未支付" 或数字 0/1/2？
    - 字符串拼错（"未支符"）编译器不报错，运行时才炸
    - 数字可读性差
    - 枚举是【类型安全】的：写错编译期就报错，IDE 还能自动补全
  命名习惯：枚举常量全大写。

【2.2 封装：private / final / getter / setter】
  private = 不给你看（外部拿不到字段）
  final   = 不给你改（只能赋一次值，可在声明时或构造方法里赋值）

  final 的效果：别人写 order.amount = 99999; 会【编译期报错】，
  等于把"不许改"交给编译器拦，而不是指望大家自觉。

  口诀：订单号、金额是"刻在石头上"的事实 -> 加 final
        状态是"白板上的字" -> 不加 final

  如果给 status 也加 final：
    setStatus 方法体里 `this.status = status;` 编译不过 -> "支付"功能写代码阶段就废了

  getter / setter（访问器）：
    getter：public 类型 getXxx() { return 字段; }
    setter：public void setXxx(类型 参数) { this.字段 = 参数; }
    （boolean 字段用 isXxx()）

  为什么要它俩？不能直接 public String id; 吗？
    能，但等于把字段敞开摆在大街上：谁都能随手改，业务规则没地方拦。
    有了 getter/setter，字段还是私有，但开了两扇"有门的通道"，门可以装锁：

      public void setAmount(int amount) {
          if (amount <= 0) throw new IllegalArgumentException("金额必须大于 0");
          this.amount = amount;
      }

  this 是什么？参数名和字段名重名时，this.字段 明确指"这个对象的字段"。

  ★【有没有 setter】本身就在表达设计意图：
      id 没 setter      -> 身份不能变
      amount 没 setter  -> 事实不能变
      status 有 setStatus -> 因为状态本来就要变
    开放得不多不少，刚刚好。

【2.3 构造方法】
  public Order(String id, int amount, OrderStatus status) {
      this.id = id; this.amount = amount; this.status = status;
  }
  作用：创建对象时一次性把字段填好。final 字段必须在这里（或声明时）赋值。

【2.4 toString 与 @Override】
  System.out.println(order) 会自动调用对象的 toString()。
  不重写 -> 打印 Order@1b6d3586（类名@十六进制），人看不懂
  重写后 -> A001 | 金额 100 | 状态 UNPAID
  口诀：println 打印什么由 toString() 决定；不写，就只给你一串"身份证号"。
  重写时加 @Override（让编译器帮你检查方法签名有没有写错）。

【2.5 异常：throw 和 try/catch】
  抛出： throw new IllegalArgumentException("金额必须大于 0");
  接住：
      try {
          int amount = Integer.parseInt(amountText);   // "100" -> 100
          Order order = service.createOrder(id, amount);
      } catch (NumberFormatException e) {              // 不是数字
          System.out.println("金额必须是数字");
      } catch (IllegalArgumentException e) {           // 业务校验不通过
          System.out.println("创建失败：" + e.getMessage());
      }

  什么时候"抛异常"、什么时候"返回 false"？（重要）
    情况不同：
      - 调用方【给错了数据】（金额传 -5、订单号重复）-> throw，
        因为这是不该发生的，要大声喊出来
      - 【正常可预期的业务结果】（订单不存在、已支付不能再付）-> return false
    口诀："是你给错了" -> 抛异常；"是正常结果" -> 返回 false

【2.6 null 与空指针（NPE）】
  错误写法： if (id.trim().isEmpty())       // id 是 null 时 -> NullPointerException，程序崩
  正确写法： if (id == null || id.trim().isEmpty())
  ★ 顺序是故意的！Java 的 || 是【从左到右、短路】的，
    id == null 为真时，右边不再执行，所以不会 NPE。

【2.7 可变 vs 不可变（设计原则）】
  "能不变就不变；非要变，也只开放必须变的那一小部分。"
  想要"金额可改"时，三种做法：
    1) 去掉 final + 加 public setAmount    -> 谁都能随时改，规则没地方拦
    2) 保留私有 + 提供带校验的 correctAmount（推荐）-> 能改，且必须过规则
    3) 干脆不改，作废这张、重开一张        -> 最干净，保留完整历史


【2.8 BigDecimal：钱必须用它】

  三种选择的对比：

      int    ：存不了小数（金额常有"分"，如 99.99）
      double ：二进制浮点无法精确表示十进制小数 —— 实测：
                 0.1 + 0.2 = 0.30000000000000004
               钱算错了是事故，所以货币绝不能用 double / float
      BigDecimal：精确十进制，专为货币与科学计算设计

  数据库对应类型：DECIMAL(12,2)
      DECIMAL(总位数, 小数位数) —— 12 位、其中 2 位小数，最大 9999999999.99

  ★ 三个必须记住的坑：

    1) 累加时必须接收返回值（BigDecimal 不可变！）

        BigDecimal sum = BigDecimal.ZERO;
        sum.add(x);              // ❌ 白算！sum 还是 0（返回值被丢了）
        sum = sum.add(x);        // ✅

       ★ 这个错误【不会编译报错、不会运行报错】，只是结果不对 —— 极危险。

    2) 比较相等【不能用 equals】，要用 compareTo

        new BigDecimal("100").equals(new BigDecimal("100.00"))    -> false ！（精度不同）
        new BigDecimal("100").compareTo(new BigDecimal("100.00")) -> 0      （只比数值）

    3) 构造时【传字符串】，不要传 double

        new BigDecimal(0.1)     // ❌ 会把 double 的误差原样带进来：0.1000000000000000055511151231257827021181583404541015625
        new BigDecimal("0.1")   // ✅ 精确

  比较大小的写法（别用 < > 运算符，BigDecimal 没有）：

        if (amount.compareTo(BigDecimal.ZERO) <= 0) { ... }   // 相当于 amount <= 0

  ★ 精度统一（scale）：
     new BigDecimal("100")   -> scale 0
     new BigDecimal("100.00")-> scale 2
     本项目在创建订单时统一 setScale(2)，
     保证数据库里、接口返回的 JSON 里金额格式一致（100 -> 100.00）。
     scale() 还可以用来做校验：scale > 2 就说明传了"厘"以下的精度，可以拒绝。

  ★ 面试话术："金额我用 BigDecimal，数据库用 DECIMAL(12,2)。
    因为 double 是二进制浮点，0.1 + 0.2 会得到 0.30000000000000004；
    另外 BigDecimal 不可变，add 要接收返回值，比较要用 compareTo 而不是 equals。"

三、集合：用 Map 当数据库
============================================================

【3.1 Map<K,V>】
  Map<String, Order> orders = new LinkedHashMap<>();
  键 = 订单号，值 = 订单对象。相当于一本字典：查"订单号" -> 得到那笔订单。

【3.2 为什么不用 List？】
  Map 能【按订单号一步查到】；List 要从头一个个翻。订单越多差距越大。

【3.3 LinkedHashMap 与 HashMap 的区别】
  LinkedHashMap 额外记住【插入顺序】，所以"查看全部"会按创建顺序显示，不乱七八糟。
  （数据库里的等价做法：加一个自增主键 seq，ORDER BY seq）

【3.4 常用方法】
  put(键, 值)          放进去
  get(键)              按键取，没有返回 null
  containsKey(键)      这个键在不在
  size()               里面有几个
  values()             取出所有"值"
  isEmpty()            （List/Map 都有）是不是空的

【3.5 put 的坑（重要）】
  Map 的 put：如果键已存在，会【直接把旧值覆盖掉】。
  所以没有"防重复"检查时，重复创建 = 静默丢数据（程序不报错，数据悄悄少了）。
  这就是 createOrder 里必须先 repository.contains(id) 的原因。

【3.6 防御性拷贝】
  错误： return orders.values();
        -> 给出去的是 Map 内部集合本身（视图），外部能 add/remove，
           等于把仓库钥匙给了别人，封装白做
  正确： return new ArrayList<>(orders.values());
        -> 复制一份新列表再给出去，别人怎么折腾都动不了你的数据

四、业务层设计原则
============================================================

【4.1 依赖注入（DI）—— 后端最核心的思想之一】
  public OrderService(OrderRepository repository) {   // 从外面传进来
      this.repository = repository;
  }

  为什么不直接在 OrderService 里 new OrderRepository()？
    - 那样"用哪个仓库"就焊死在 OrderService 里了，换数据库必须回来改它
    - 从外面递进来，OrderService 只管用，换成什么仓库都不关心
    - 附带好处：测试时可以塞一个"假仓库"进去
  一句话：我需要的零件，你递给我，别让我自己造。

【4.2 校验要放在业务层】
  OrderRepository 只会傻乎乎地 put（存），
  "什么情况不许存"这种判断，只能由 OrderService 把关。

【4.3 卫语句（guard clause）】
  先把异常情况挡在最前面，剩下的代码就都是"正常路径"，不用嵌套。

    // 推荐
    if (order == null) throw ...;
    return order;

    // 等价但正常逻辑被挤进 else，逻辑长了读起来累
    if (order != null) return order; else throw ...;

【4.4 createOrder 的三道校验（顺序不能错）】
  1) 订单号不能为空   （先判 null，再判 trim 后是否为空 —— 顺序反了会 NPE）
  2) 金额必须大于 0
  3) 订单号不能重复   （用 repository.contains(id)）
  全通过后：new Order(id, amount, UNPAID) -> repository.add(order) -> return order

五、Maven 工程化
============================================================

【5.1 标准目录结构（全世界的 Java 项目都这样）】
  pom.xml                          项目说明书：依赖、编译版本、插件
  src/main/java/...                源码
  src/main/resources/
      application.properties       配置（数据库地址等）
      schema.sql                   建表脚本
  src/test/java/...                测试代码
  src/test/resources/
      application.properties       测试专用配置（用内存数据库）
  target/                          构建产物（不用管，也别提交到 Git）

【5.2 pom.xml 各部分的含义】
  <parent>       继承 Spring Boot 官方父 POM -> 依赖版本由它统一管理
  <groupId>      组织名，如 com.example
  <artifactId>   项目名，如 order-app
  <version>      版本号，如 1.0.0
  <properties>   java.version=21（父 POM 认这个属性决定编译版本）
  <dependencies> 依赖清单
  <scope>test</scope>     只在测试时用，不进最终程序
  <scope>runtime</scope>  编译时不用、运行时才需要（如数据库驱动）
  <build><plugins>  spring-boot-maven-plugin（提供 run 命令、打可执行 jar）

【5.3 常用命令】
  mvn compile              编译
  mvn test                 编译 + 跑测试
  mvn spring-boot:run      启动 Spring Boot 服务
  mvn package              打包成 jar
  mvn -q xxx               安静模式（少打日志）
  mvn -B xxx               批处理模式（日志更干净，适合脚本）

【5.4 中文乱码的两个处理】
  javac 源码编码：   javac -encoding UTF-8 ...
  Java 运行输出编码： java -Dstdout.encoding=UTF-8 -Dstdin.encoding=UTF-8 ...
  Maven 报错乱码：   编译前执行 $env:JAVA_TOOL_OPTIONS = "-Duser.language=en -Duser.country=US"

【5.5 怎么读编译报错】
  src\OrderRepository.java:19: error: cannot find symbol
      public ListAll<Order> getAll() {
             ^
    symbol:   class ListAll
  三段信息：哪个文件:第几行 -> 错误类型 -> ^ 箭头指着出问题的地方
  ★ 编译器不报错 != 代码写对了（编译器只认语法，不认你的意图）


【5.6 持续集成（CI）：让"每次提交都自动验证"】

  问题：本地跑通不代表别人拉下来也能跑通；也防不住"改坏了没发现就提交"。

  做法：在仓库里放一个 .github/workflows/ci.yml，GitHub 就会在指定时机自动跑：

      name: CI
      on:
        push:
          branches: [ main ]
        pull_request:
      jobs:
        build:
          runs-on: ubuntu-latest
          steps:
            - uses: actions/checkout@v4                      # 拉代码
            - uses: actions/setup-java@v4                    # 装 JDK
              with:
                java-version: '21'
                distribution: 'temurin'
                cache: maven                                 # 缓存依赖，加速
            - run: mvn -B clean verify                       # 编译 + 测试 + 打包

  几个要点：
    - on: 是触发时机（push / pull_request / schedule...）
    - setup-java 的 java-version 要和 pom.xml 的 java.version 一致
    - cache: maven 会缓存 ~/.m2，第二次起构建快很多
    - mvn -B clean verify：clean 保证全新构建，verify 会跑完测试并打包
    - -B 是批处理模式，日志更干净（适合 CI）

  ★ 简历小技巧：README 顶部加一个状态徽章，一眼就能看到"测试是通过的"：

      ![CI](https://github.com/<用户名>/<仓库>/actions/workflows/ci.yml/badge.svg)

  ★ 关键认知：CI 的价值不只是"自动跑测试"，而是
    【把"能不能构建、测试过不过"变成对所有人可见的事实】——
    别人（包括面试官）点开仓库就能看到绿标。


【5.7 CI 里跑真 MySQL：services + 环境变量覆盖】

  问题：CI 默认在 H2 内存库上跑测试。H2 是"仿真"数据库，和真 MySQL 有差异：
        字符集（中文变 ??）、严格模式（超长字符串是报错还是截断）、
        自增、外键、GROUP BY 行为……
        在 H2 上全绿 != 在 MySQL 上也全绿。

  做法：让 GitHub Actions 额外起一个 MySQL 容器（等价于本地 docker compose up），
        再用【环境变量】把测试数据源指过去 —— 一行 Java 代码都不用改。

    jobs:
      test-mysql:
        runs-on: ubuntu-latest
        services:                          # ★ 关键：service container
          mysql:
            image: mysql:8.4
            env:
              MYSQL_ROOT_PASSWORD: root
              MYSQL_DATABASE: orderdb
              MYSQL_USER: order
              MYSQL_PASSWORD: order123
            ports:
              - 3306:3306
            options: >-                    # ★ 健康检查
              --health-cmd="mysqladmin ping -h 127.0.0.1 -u root -proot --silent"
              --health-interval=10s
              --health-timeout=5s
              --health-retries=12
        env:
          SPRING_DATASOURCE_URL: jdbc:mysql://127.0.0.1:3306/orderdb?...&allowPublicKeyRetrieval=true
          SPRING_DATASOURCE_DRIVER_CLASS_NAME: com.mysql.cj.jdbc.Driver
          SPRING_DATASOURCE_USERNAME: order
          SPRING_DATASOURCE_PASSWORD: order123
          EXPECT_DB: mysql
        steps:
          - uses: actions/checkout@v4
          - uses: actions/setup-java@v4
            with: { java-version: '21', distribution: 'temurin', cache: maven }
          - run: mvn -B clean verify

  ★ 为什么不用改配置文件？（务必理解这条）
    Spring Boot 配置优先级：
        命令行参数  >  环境变量  >  application.properties
    且环境变量是"宽松绑定"（relaxed binding）：
        SPRING_DATASOURCE_URL                -> spring.datasource.url
        SPRING_DATASOURCE_DRIVER_CLASS_NAME  -> spring.datasource.driver-class-name
    所以 src/test/resources/application.properties 里写死的 H2 配置会被覆盖。
    这个手法叫【配置外置】（12-Factor App）：
    同一份构建产物，靠外部注入的配置跑在不同环境。

  ★ 坑 1：容器"启动了"不等于数据库"能连"
    mysqld 起来后还要初始化数据目录，前几秒端口连不上。
    - 用 services.mysql.options 的 --health-cmd，GitHub 会等 healthy 再继续
    - 再补一层端口探测更稳：
        for i in $(seq 1 30); do
          (echo > /dev/tcp/127.0.0.1/3306) 2>/dev/null && exit 0
          sleep 2
        done; exit 1

  ★ 坑 2：环境变量拼错，Spring 会【静默忽略】，流水线就"说谎"了
    比如把 SPRING_DATASOURCE_URL 写成 SPRING_DATASOURCE_URI，
    不报错、不警告，测试照样在 H2 上全绿 —— 但 CI 报告"MySQL 通过"。
    防法：加一个守卫测试，主动断言"我到底连的是谁"：

        String expected = System.getenv("EXPECT_DB");
        assumeTrue(expected != null, "未设置 EXPECT_DB，跳过");
        String url = dataSource.getConnection().getMetaData().getURL();
        assertTrue(url.toLowerCase().contains(expected), "期望 " + expected + "，实际 " + url);

    CI 里设 EXPECT_DB=mysql 就必须连上 MySQL；本地不设则自动 skip。
    ★ 这个思路可以反复用：凡是"靠外部配置切换行为"的地方，都值得加一条断言。

  ★ 坑 3：测试之间的数据隔离
    本项目每个测试类都有 @BeforeEach 清表（先删 order_items 再删 orders，
    因为有外键）。换到 MySQL 后这一点不变，所以整套测试可以原样迁移。
    如果测试依赖"空表"却没清理，在 H2 上可能侥幸通过，
    在 MySQL 上就会因残留数据而随机失败（flaky test）。

  ★ 坑 4：SQL 方言差异
    - 迁移前先确认建表脚本两边都能跑（本项目 schema.sql 用
      CREATE TABLE IF NOT EXISTS，MySQL 与 H2 通用）
    - 断言不要依赖数据库错误文案（H2 和 MySQL 的报错文字完全不同），
      要断言【异常类型】（本项目断言 DataIntegrityViolationException）
    - 中文测试数据一定要在 URL 里带 characterEncoding=utf8

  ★ 坑 5：CI 失败时看不到细节
    控制台日志又长又乱。加一步在失败时上传测试报告：

        - if: failure()
          uses: actions/upload-artifact@v4
          with:
            name: surefire-reports
            path: target/surefire-reports/

  ★ 面试话术：
    "CI 我跑两个 job：H2 那个几十秒出结果，负责快速反馈；
     另一个用 service container 起 MySQL 8，跑同一套测试，
     通过注入 SPRING_DATASOURCE_* 环境变量切换数据源，
     同一份代码不改造就能验真库。
     另外加了一个数据源守卫测试，防止环境变量拼错导致
     测试偷偷跑在 H2 上、CI 却显示 MySQL 通过。"


============================================================
六、单元测试（JUnit 5）
============================================================

【6.1 是什么、为什么要写】
  一段自动运行的代码，用来验证行为对不对。
  以前验证功能要手敲菜单，又慢又容易漏；现在改一行代码 -> mvn test -> 3 秒告诉你有没有弄坏。
  面试必问：它证明你写的不只是"能跑"，而是"能保证对"。

【6.2 三个核心】
  1) 测试方法带 @Test 注解（没它 JUnit 当这个方法是空气 —— 会白写）
  2) AAA 模式：Arrange 准备 -> Act 执行 -> Assert 断言
  3) @BeforeEach：每个测试方法执行前都先跑一次，保证测试之间互不干扰

【6.3 断言方法】
  assertEquals(期望值, 实际值)      两者相等吗（期望在前，别写反）
  assertTrue(x) / assertFalse(x)    真 / 假
  assertNull(x) / assertNotNull(x)  空 / 非空
  assertThrows(异常类.class, () -> { ... })   这段代码应该抛异常，否则测试失败

  () -> service.createOrder("A001", 0) 是 lambda：
  把这段代码包起来先不执行，交给 assertThrows 去执行。

【6.4 怎么读测试失败（很有价值）】
  org.opentest4j.AssertionFailedError: expected: <订单号已存在> but was: <订单号已存在：A001>
  expected = 你期望的；but was = 代码实际给出的。
  ★ 这不一定是"代码有 bug"，可能是"你的期望写得不够精确"。
    真实故事：测试发现错误信息其实带上了订单号（"订单号已存在：A001"），
    而人以为只有"订单号已存在" —— 测试帮你看清了真实行为。
  两种修法：
    A) assertEquals("订单号已存在：A001", e.getMessage());   期望写精确
    B) assertTrue(e.getMessage().contains("订单号已存在"));  只检查包含（更抗改动）

【6.5 测试文件的两条硬性规矩】
  1) 文件名必须以 Test 结尾（Maven 靠这个找测试）
  2) 必须放在 src/test/java 下（放错地方 = 不编译也不运行，一声不响）

【6.6 有了数据库之后，测试怎么写】
  @SpringBootTest                 启动 Spring 上下文（不再手动 new）
  @Autowired OrderService service;  让 Spring 把对象递进来
  @Autowired JdbcTemplate jdbc;
  @BeforeEach void setUp() { jdbc.update("DELETE FROM orders"); }   // 每个测试前清表
  测试代码本身（断言部分）几乎不用改 —— 这就是分层的好处。

【6.7 分层测试：业务层 vs 接口层】

  两层测试分工不同（本项目共 22 个测试）：

      业务层（OrderServiceTest，8 个）
          直接调用 Java 方法，测的是【逻辑对不对】
          service.createOrder("A001", 100)
          assertThrows(IllegalArgumentException.class, () -> ...)

      接口层（OrderControllerTest，14 个）
          用 MockMvc 模拟 HTTP 请求，测的是【HTTP 契约对不对】
          状态码、JSON 字段名、错误格式、DTO 白名单

  接口层测试需要的注解（比业务层多一个）：

      @SpringBootTest
      @AutoConfigureMockMvc               // 加这个才能注入 MockMvc
      class OrderControllerTest {

          @Autowired MockMvc mockMvc;     // 它能在不启动 Tomcat 的情况下"发 HTTP 请求"
          @Autowired OrderService service;   // 用来准备数据
          @Autowired JdbcTemplate jdbc;      // 用来清表

  怎么发请求（固定套路，记住四个方法）：

      mockMvc.perform(post("/orders")
                      .contentType(MediaType.APPLICATION_JSON)
                      .content("{\"id\":\"A001\",\"amount\":100}"))
             .andExpect(status().isCreated())                    // 断言状态码
             .andExpect(jsonPath("$.id").value("A001"))          // 断言 JSON 字段
             .andExpect(jsonPath("$.error").value("订单号不能为空"));

      get(...)  / post(...)                发请求
      status().isOk() / isCreated() / isBadRequest() / isNotFound() / isConflict()
      jsonPath("$.字段名").value(期望值)     断言 JSON 内容
      jsonPath("$.length()").value(2)      断言数组长度
      jsonPath("$[0].id")                  数组第 0 个元素的 id

  ★ MockMvc 的好处：不用真的启动服务器、不用管端口，就能测完整的
    "请求 -> 拦截 -> Controller -> Service -> 数据库 -> 响应"链路。

【6.8 一个很值得写的接口层测试：DTO 白名单】

  验证"客户端多传字段会被忽略"，这是防参数注入的证据：

      @Test
      void create_extraFieldsAreIgnored() throws Exception {
          mockMvc.perform(post("/orders")
                          .contentType(MediaType.APPLICATION_JSON)
                          .content("{\"id\":\"A001\",\"amount\":100,\"status\":\"PAID\",\"seq\":9999}"))
                 .andExpect(status().isCreated())
                 .andExpect(jsonPath("$.status").value("UNPAID"));   // 没被篡改
      }

  如果接口用实体接收请求体，status 就会变成 PAID —— 等于绕过支付流程。
  详见第十三节和 DTO 相关说明。

【6.9 跑测试的常用命令】

      mvn test                                跑全部
      mvn clean test                          先清理再跑（改了构造方法/签名后建议用这个）
      mvn test -Dtest=OrderControllerTest     只跑某一个测试类
      mvn test -Dtest=OrderServiceTest#pay_concurrentOnlyOneSucceeds   只跑某一个方法

  ★ 为什么建议改签名后用 clean test：
    Maven 默认做【增量编译】，只重编"时间戳变了"的文件。
    如果改了 A 的构造方法、但 B 的源文件没动，B 可能【跳过重编】，
    于是编译错误被掩盖，直到某次全量编译才突然爆出来。


============================================================
七、Spring Boot 与 Web 接口
============================================================

【7.1 注解是什么】
  注解本身什么都不干，它只是一张"贴纸"（元数据），作用是给框架留记号。
  就像行李箱上的"易碎品"标签：标签不保护箱子，是搬运工看到标签后改变了做法。
  一句话：注解 = 给框架看的贴纸。你贴标签表达意图，框架读标签干活。
  没有注解的年代，要用 XML 把关系一条条写出来，烦到出名。

【7.2 启动时发生了什么】
  1. JVM 执行 OrderAppApplication.main()
  2. 看到 @SpringBootApplication -> 开始扫描 com.example.order 包
  3. 读所有类身上的"贴纸"：
       发现 @Service     -> new OrderService()，放进对象池
       发现 @Repository  -> new OrderRepository()，放进对象池
       发现 @RestController -> 看构造方法需要 OrderService -> 从对象池捞出来塞进去（依赖注入）
       发现 @GetMapping / @PostMapping -> 记下路由表
  4. 启动 Tomcat，监听 8080
  5. 浏览器来请求 -> 查路由表 -> 调用对应方法 -> 返回 JSON

【7.3 注解分类速查】
  【身份】@SpringBootApplication  从这儿开始（自动配置 + 组件扫描）
          @Service               交给 Spring 管（业务层）
          @Repository            交给 Spring 管（数据层）
          @RestController        交给 Spring 管 + 处理 HTTP 请求
              （这几个功能本质一样，名字不同是为了表达角色）
  【路由】@RequestMapping("/orders")  贴在类上，公共前缀
          @GetMapping             处理 GET
          @PostMapping            处理 POST
          @GetMapping("/{id}")    花括号 = 路径占位符（变量，不是固定文字）
  【取数据】@PathVariable          从 URL 路径取值：/orders/A001 -> id="A001"
            @RequestBody           从请求体取 JSON，并自动转成 Java 对象
  【回复】  @ResponseStatus(HttpStatus.CREATED)  强制指定成功状态码（默认 200）
            返回对象 -> Spring 自动转 JSON
  【异常】  @RestControllerAdvice      全局兜底，所有 Controller 的异常都归我管
            @ExceptionHandler(异常类.class)  这类异常交给下面这个方法处理
  【测试】  @Test / @BeforeEach / @SpringBootTest / @Autowired

【7.4 完整地址怎么来的】
  @RequestMapping("/orders")   ← 类上前缀
  @GetMapping("/{id}")         ← 方法上后缀
  -------------------------------------------------
  合起来：GET /orders/{id}

【7.5 record（Java 16+）】
  record CreateOrderRequest(String id, int amount) { }
  "只装数据的类"，一行顶过去十几行（自动生成构造方法、getter、equals 等）。
  取值用 request.id()、request.amount()（注意是 id() 不是 getId()）。

【7.6 JSON 是怎么来的（为什么 getter 很重要）】
  返回 Order 对象，Spring 用 Jackson 自动序列化成：
    {"id":"A001","amount":100,"status":"UNPAID"}
  Jackson 靠 getter 取名字：getAmount() -> JSON 里的 amount。
  发过来的 JSON 也要靠字段名匹配：字段名必须和 JSON 的 key 一致，否则塞不进去。

【7.7 把 Java 异常翻译成 HTTP】
  ApiExceptionHandler 接住 OrderService 抛的 IllegalArgumentException：
    返回 HTTP 400 + {"error":"金额必须大于 0"}
  对比控制台版的 try/catch + println —— 同一件事，两种表达方式。
  Web 版把它变成了全局的、写一次管所有接口。

【7.8 ResponseStatusException 还是 ResponseEntity？】
  两种等价写法：
    A) throw new ResponseStatusException(HttpStatus.NOT_FOUND, "订单不存在：" + id);
       方法返回类型干净（就是 Order）；错误靠"抛"。适合错误是少数情况。
    B) public ResponseEntity<Order> getOne(...) {
           if (order == null) return ResponseEntity.notFound().build();
           return ResponseEntity.ok(order);
       }
       返回类型里就带着状态码，一目了然。适合一个方法要返回多种状态码。
  团队统一用一种就行，别混着用。

【7.9 为什么"查不到"不能直接 return null（大坑）】
  public Order getOne(@PathVariable String id) {
      return service.findOrder(id);      // 查不到时返回 null
  }
  结果：HTTP 200 + 空响应体。客户端以为"成功了，订单就是这个（空的）"——【假成功】。
  原则：错误必须"响亮"地表达出来（404 + 错误信息），不能悄悄返回空值让调用方猜。

【7.10 Swagger UI（springdoc-openapi，零代码生成接口文档）】
  依赖：org.springdoc:springdoc-openapi-starter-webmvc-ui
  自动扫描 @RestController，生成可视化页面，点按钮就能调接口。
  地址：
    /swagger-ui.html     人类看的图形界面
    /v3/api-docs         机器看的 JSON（Postman 能一键导入）
  用法：展开接口 -> Try it out -> 填参数/请求体 -> Execute -> 看 Server response


【7.11 日志（SLF4J）：怎么让程序"会说话"】

  为什么需要日志？
    出问题时（用户说"我支付失败了"），你要能回答：
      什么时候、哪个请求、发生了什么、为什么失败。
    光靠 System.out.println 不行（没有级别、没有时间、没法按包开关、生产环境不该往控制台打）。

  Spring Boot 内置 SLF4J + Logback，直接用：

      private static final Logger log = LoggerFactory.getLogger(OrderService.class);
      // import org.slf4j.Logger;
      // import org.slf4j.LoggerFactory;

      log.info("创建订单成功: id={}, amount={}", id, amount);
      log.warn("创建订单时发生订单号冲突（并发）: id={}", id);
      log.error("未预期的异常", e);        // 注意：异常对象作为【最后一个参数】，会自动打全栈

  五个级别（从低到高）：trace < debug < info < warn < error
    默认显示 info 及以上。

  ★ 用 {} 占位符，不要字符串拼接：
      log.info("id=" + id);            // ❌ 没开 info 级别也白拼了字符串
      log.info("id={}", id);           // ✅ 级别不够就不拼，零开销

  日志级别的选择（约定）：
      info  —— 状态变更成功（创建/支付/取消成功），能还原"谁做了什么"
      warn  —— 可预期的失败（订单不存在、状态冲突），需要追溯但不报警
      error —— 未预期异常（代码 bug、环境问题），必须打完整堆栈

  ★ 两句话原则（很重要）：
      日志里说全话 —— log.error("未预期的异常", e)  打全栈，方便排查
      响应里说最少话 —— {"error":"服务器内部错误"}   不暴露堆栈/SQL/类名

  怎么按包调级别（application.properties）：
      logging.level.com.example.order=INFO
      logging.level.org.springframework.jdbc.core=DEBUG   # 想看每条 SQL 和参数时打开

  ★ 面试话术："我的日志分了级别——状态变更记 info 便于追溯，业务失败记 warn，
    未预期异常在全局处理器里记 error 并打全栈，同时对外只返回一句通用提示，
    避免泄露内部实现。"


============================================================
八、持久化：从内存到数据库
============================================================

【8.1 为什么必须做】
  内存 Map 的致命问题：服务一重启，数据全没了。
  真实业务（订单、用户、支付）必须持久化，否则毫无意义。

【8.2 选型：H2 文件模式】
  - H2 是纯 Java 的内嵌数据库，加个依赖就能用，不用单独安装
  - 文件模式：数据存在项目下的 data\orderdb.mv.db 文件里，重启不丢
  - 想换成 MySQL 只要改 application.properties 的 url/driver/用户名密码
  依赖：
    spring-boot-starter-jdbc        提供 JdbcTemplate + HikariCP 连接池
    com.h2database:h2 (runtime)     数据库驱动

【8.3 关键配置 application.properties】
  spring.datasource.url=jdbc:h2:file:./data/orderdb    文件模式
  spring.datasource.driver-class-name=org.h2.Driver
  spring.datasource.username=sa
  spring.datasource.password=
  spring.sql.init.mode=always           每次启动都执行 schema.sql
  spring.h2.console.enabled=true        打开 /h2-console 数据库控制台
  测试专用 src/test/resources/application.properties：
    spring.datasource.url=jdbc:h2:mem:testdb    内存模式，跑完就消失，不污染真实数据

【8.4 建表脚本 schema.sql】
  CREATE TABLE IF NOT EXISTS orders (
      seq    BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 自增序号，保持插入顺序（等价 LinkedHashMap）
      id     VARCHAR(64) NOT NULL UNIQUE,        -- 订单号，唯一约束（数据库再兜一层底）
      amount INT         NOT NULL,               -- 金额
      status VARCHAR(16) NOT NULL                -- 状态，存枚举的 name()
  );
  IF NOT EXISTS 保证脚本可重复执行（每次启动都会跑）。

【8.5 JdbcTemplate 常用方法】
  jdbc.update("INSERT INTO orders (id, amount, status) VALUES (?, ?, ?)", a, b, c);
      执行增删改；? 是占位符，后面的参数按顺序填进去（防 SQL 注入）
  jdbc.query("SELECT ... WHERE id = ?", RowMapper, id);
      查询，每一行交给 RowMapper 变成 Java 对象，返回 List
  jdbc.queryForObject("SELECT COUNT(*) FROM orders WHERE id = ?", Integer.class, id);
      查询单个值

【8.6 RowMapper：把一行数据库记录变回对象】
  private static final RowMapper<Order> TO_ORDER = (rs, rowNum) -> new Order(
          rs.getString("id"),
          rs.getInt("amount"),
          OrderStatus.valueOf(rs.getString("status"))
  );
  rs = ResultSet（结果集），rs.getString("列名") 按列名取值。

【8.7 SQL 基础速查】
  SELECT 列1, 列2 FROM 表 WHERE 条件 ORDER BY 列
  INSERT INTO 表 (列...) VALUES (值...)
  UPDATE 表 SET 列 = 值 WHERE 条件      ★ 忘了 WHERE 会改全表
  SELECT COUNT(*) FROM 表 WHERE 条件   数一数有几行
  AUTO_INCREMENT 自增主键；UNIQUE 唯一约束

【8.8 ★★ 最重要的观念变化：内存"共享对象" vs 数据库"必须写回"】

  内存版（旧）：
      Order order = repository.get(id);     // 拿到的是 Map 里【同一个对象】
      order.setStatus(PAID);                // 改它 = 直接改了 Map 里的对象，自动生效
      return true;                          // 不用保存

  数据库版（新）：
      Order order = repository.get(id);     // 拿到的是【新造的对象】，数据库里那份没变
      order.setStatus(PAID);                // 只改了内存里的这个副本
      repository.update(order);             // ★ 必须显式写回数据库（UPDATE）
      return true;

  一句话：内存靠"对象引用共享"自动同步；数据库必须【显式保存】。
  漏了 update(...) 的后果：接口返回"支付成功"，但重启后状态还是 UNPAID（假成功）。

【8.9 换数据库只改了一个文件（分层的价值）】
  改动清单：
    pom.xml                  加 jdbc + h2 依赖
    src/main/resources/      加 application.properties、schema.sql
    OrderRepository.java     重写方法体（Map -> SQL）
    OrderService.java        pay / cancel 各加一句 repository.update(order)
    OrderServiceTest.java    改成 @SpringBootTest + 清表
  没动：OrderController.java、Order.java、OrderStatus.java、ApiExceptionHandler.java

【8.10 分页：为什么必须做、怎么做】

  为什么不能"一次返回全部"？
    - 内存：10 万条一次性读进 List，可能直接 OOM（内存溢出）
    - 速度：传输 + 序列化 10 万条 JSON，响应几秒甚至超时
    - 数据库：大结果集长时间占用连接和 IO
  分页 = 让客户端"一页一页拿"，每次只取固定条数。

  ★ 关键：分页要【由数据库完成】，不是查出来再截断

      // ❌ 假分页：还是把全表读进了内存，只是返回时少给几条
      List<Order> all = repository.listAll();
      return all.subList(offset, min(all.size(), offset + size));

      // ✅ 真分页：让数据库只返回需要的行
      SELECT id, amount, status FROM orders ORDER BY seq LIMIT ? OFFSET ?;
      // 参数：limit=每页条数, offset=(page-1)*size

    （H2、MySQL、PostgreSQL 都支持 LIMIT ? OFFSET ? 这种写法。）

  ★ 两个最容易被问/最容易写错的点：

    1) 偏移量怎么算：offset = (page - 1) * size
       第 1 页 -> 0（从第一条开始）；第 2 页 -> size（跳过第一页的 size 条）
       写错就出现"第 2 页重复出现第 1 页最后一条"这类 off-by-one bug。

    2) size 必须有上限！
       如果允许 size=999999，客户端一请求就等于把全表拉走了 —— 等于没分页。
       所以业务层校验：1 <= size <= 100（本项目 MAX_PAGE_SIZE）。

  ★ 返回结构（不要只返回个数组，客户端算不出总数）：

      {
        "items": [ ... ],     // 当前页数据
        "total": 25,          // 总记录数
        "page": 1,            // 当前页码（本项目从 1 开始）
        "size": 10,           // 每页条数
        "totalPages": 3       // 总页数 = ceil(total / size)
      }

    总页数向上取整的写法：(total + size - 1) / size
      例：25 条 / 每页 10 条 -> (25 + 9) / 10 = 3 页

  ★ 页码从 0 还是从 1 开始？
    两种都在用：Spring Data 习惯从 0 开始，很多面向人的 API 从 1 开始。
    没有对错，关键是【项目内统一】并且【写进文档】。本项目用 1 开始。

  ★ 一个通用技巧：PageResponse<T> 用泛型 + map()
    业务层返回 PageResponse<Order>，接口层一行转换成 PageResponse<OrderResponse>：

        return service.listOrders(page, size).map(OrderResponse::from);

    分页信息（total/page/size）原样保留，只有 items 的元素类型变了。

  ★ 坑：Jackson 只认 getXxx() 命名
    记录类里写 totalPages() 不会出现在 JSON 里，要写成 getTotalPages()。

  ★ 顺带一提：本项目 sumAmount 仍是"查出全部再累加"，
    数据量大时也应该改成让数据库算聚合：
        SELECT SUM(amount) FROM orders WHERE status = ?
    —— 同样是"别把全表读进内存"的思路。


============================================================
九、HTTP 状态码速查
============================================================

  200 OK            正常返回
  201 Created       创建成功（POST /orders）
  400 Bad Request   参数不合法（订单号空、金额<=0、订单号重复）—— ApiExceptionHandler 自动处理
  404 Not Found     资源不存在（查不到这个订单）
  409 Conflict      状态冲突（已支付的订单又想支付/取消）
  500 Internal Server Error  服务器自己出了 bug（比如空指针）

  为什么 404 不是 400？
    400 = 你的请求（参数）有毛病
    404 = 你要的东西不存在
    409 = 东西在，但现在这个状态不允许你这么干

【9.1 统一错误响应格式（重要）】

  所有错误响应都统一成一种结构：

      {"error": "错误原因"}

  为什么必须统一？
    - 客户端只需处理一种结构，代码简单
    - 避免落到 Spring 的默认错误页，它返回的是：
        {"timestamp":"2026-...","status":404,"error":"Not Found","path":"/orders/xxx"}
      两个问题：① 格式和业务错误不一致，客户端要写两套解析
                ② 泄露 timestamp / path 等内部信息

  实现（ApiExceptionHandler，@RestControllerAdvice）：
    - @ExceptionHandler(IllegalArgumentException.class)      -> 400
    - @ExceptionHandler(ResponseStatusException.class)       -> 沿用异常自带的状态码（404/409）

  坑：Map.of(...) 的值【不允许为 null】。
      异常 e.getMessage() 和 e.getReason() 都可能为 null，
      直接放进去会抛 NPE —— 要写兜底文案：

          String text = (message == null || message.isBlank()) ? fallback : message;

  ★ 进阶：让【框架自己的异常】也统一（重要）

    上面只处理了业务异常。但 Spring MVC 自己还会抛很多标准异常：

        非法 JSON        -> HttpMessageNotReadableException  -> 400
        方法不支持       -> HttpRequestMethodNotSupportedException -> 405
        Content-Type 不对 -> HttpMediaTypeNotSupportedException -> 415
        数据库异常       -> DataIntegrityViolationException  -> 500

    这些【不处理就会走 Spring 默认错误页】，返回：
        {"timestamp":"...","status":400,"error":"Bad Request","path":"/orders"}
    → 格式和业务错误不一致，客户端要写两套解析。

    正确做法：让处理器【继承 ResponseEntityExceptionHandler】

        @RestControllerAdvice
        public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

            @ExceptionHandler(IllegalArgumentException.class) ...    // 业务 400
            @ExceptionHandler(ResponseStatusException.class) ...     // 404 / 409
            @ExceptionHandler(Exception.class) ...                   // 兜底 500

            @Override
            protected ResponseEntity<Object> handleExceptionInternal(
                    Exception ex, Object body, HttpHeaders headers,
                    HttpStatusCode statusCode, WebRequest request) {  // 框架标准异常都走这里
                ...
            }
        }

    为什么继承它？
      父类【已经内置】了所有标准异常的处理，并判定好正确状态码。
      你只需重写 handleExceptionInternal 换掉响应体 ——
      既统一了格式，又不会把 400 误判成 500。

  ★ 500 的处理原则（两条，都要记）：
      日志里说全话：log.error("未预期的异常", e)   —— 打完整堆栈，便于排查
      响应里说最少话：{"error":"服务器内部错误"}    —— 不暴露堆栈、SQL、类名
    （Spring Boot 默认 server.error.include-stacktrace=never，所以默认也不会泄露，
      但格式不统一；自己兜底就能两全。）

  最后实测（8 条错误路径全部统一为 {"error": "..."}）：

      订单号为空/重复/金额非法   400
      非法 JSON                400
      查询不存在               404
      方法不支持               405
      重复支付                 409
      Content-Type 不支持      415
      数据库异常（订单号超长）  500

【9.2 状态码该由谁决定】

  经验法则：
    - 400 由【业务校验失败】触发（Service 抛 IllegalArgumentException，
      全局处理器统一转成 400）
    - 404/409 由【接口层根据业务返回的 false/null】决定
      （Service 返回 false 表示"正常业务结果"，接口层翻译成 409）
    - Service 层【不认识 HTTP】，所以它不返回状态码，只抛异常/返回布尔

【1】端口被占用
  现象：启动时 Process terminated with exit code: 1
  根因：往上看几行，会有一句 "Web server failed to start. Port 8080 was already in use."
        （最下面那堆 [ERROR] ... Help 1 是模板废话，根因在上面）
  原因：已经有一个服务在跑了（常见于自己启动了两次）
  解决：Ctrl+C 停掉旧的，或查 PID 杀进程，或换端口：
        mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8081

【2】改完代码接口还是老样子 / 404
  原因：Spring Boot 默认不热重载
  解决：Ctrl+C 后重新 mvn spring-boot:run

【3】浏览器"拒绝连接"
  原因：服务没在跑（不是代码问题）
  解决：先启动服务；用 curl 确认返回 200

【4】终端看起来"卡住了"
  现象：打完 "Started ... in x seconds" 就不动了，没有提示符
  真相：那是【服务器在正常运行】，常驻进程就该这样
  判断：另开终端 curl 一下，200 就是活着
  干活：另开一个终端（VS Code：Ctrl+Shift+`），一个跑服务、一个敲命令

【5】数据重启后全没了
  原因：数据存在内存 Map 里
  解决：做持久化（见第八节）

【6】测试放了没跑，还不报错
  原因：测试文件不在 src/test/java 下
  现象：mvn test 只显示 Nothing to compile - all classes are up to date
  解决：挪到正确目录

【7】测试方法写了但没执行
  原因：忘了 @Test 注解（没它 JUnit 当它不存在）

【8】HTTP 200 + 空响应体（假成功）
  原因：查不到时直接 return null
  解决：抛 ResponseStatusException(NOT_FOUND)

【9】数据库版忘了写回
  原因：pay/cancel 改完内存对象就 return 了，没调 repository.update()
  后果：接口说"成功"，重启一看状态没变

【10】中文乱码
  编译：javac -encoding UTF-8
  运行：-Dstdout.encoding=UTF-8 -Dstdin.encoding=UTF-8
  Maven 报错英文：$env:JAVA_TOOL_OPTIONS = "-Duser.language=en -Duser.country=US"

【11】改了构造方法/方法签名后，编译错误被"藏"起来
  原因：Maven 默认增量编译，只重编时间戳变化的文件，
        调用方的源文件没动就可能跳过重编，错误被掩盖。
  现象：改完运行正常，某次全量编译突然报错。
  解决：改签名后跑 mvn clean test。

【12】"先查后写"导致的并发问题（两个地方都踩过）
  pay/cancel：先查状态再更新 -> 并发下重复支付
    修：把条件写进 SQL 的 WHERE（原子更新）
  createOrder：先查是否存在再插入 -> 并发下撞唯一约束 -> 500
    修：捕获 DuplicateKeyException，翻译成业务错误（400）
  ★ 修完一处要主动检查同类写法还有没有别处。

【13】.properties 文件里写了行尾注释 -> 启动直接崩
  现象：Failed to bind properties under '...' to long:
        Value: "30000  # 说明文字"
  原因：# 只有出现在【行首】才是注释，写在 = 后面会成为值的一部分。
  解决：注释单独占一行。
  教训：配置改完一定要真的启动一次，光看是看不出来的。

【14】误以为"容器起来了 = 数据库能用了"
  现象：docker compose up 之后立刻启动应用，连接被拒绝。
  原因：MySQL 首次启动要初始化几十秒，这期间端口虽在监听但还不接受连接。
  解决：在 docker-compose.yml 里配 healthcheck，等 docker compose ps 显示 healthy。

【15】用 PowerShell 调接口，中文变成 ?? —— 先别怀疑代码
  现象：注册/建单后，数据库里中文变成字面的 "??"（HEX = 3F3F），
        接口返回的中文在 PowerShell 里显示成 "è¹æ" 之类的乱码。
  原因：Windows PowerShell 5.1 的 Invoke-RestMethod 默认不按 UTF-8 处理请求体和响应
        （按 ASCII / Latin-1），中文在【发送前】就已经变成 ? 了。
  判断方法（很重要）：
      用 curl 把 UTF-8 文件作为请求体上传，再查 HEX：
          SELECT product_name, HEX(product_name) FROM ...;
      如果 HEX = E88BB9E69E9C（"苹果"的正确 UTF-8 字节）→ 服务端和数据库都没问题，
      坏在客户端。
  解决：
      curl.exe -X POST ... -H "Content-Type: application/json; charset=UTF-8" --data-binary "@body.json"
      或用 PowerShell 7（默认 UTF-8）
      或 [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
  ★ 教训：验证结果反常时，先排除"测试工具/客户端"，再怀疑代码。
    这次如果直接去改 application.properties 的字符集，就是在修一个不存在的问题。

十二、面试问答速查
============================================================

Q1 介绍下你的架构？
   四层：界面层（Main / OrderController）、业务层（OrderService）、
   数据层（OrderRepository）、实体（Order / OrderStatus）。
   关键点：界面层里一个业务判断都没有，规则全在 Service —— 改规则只动一个地方。
   依赖方向单向：界面 -> 业务 -> 数据 -> 实体。

Q2 为什么订单号加 final？
   它是订单的"身份"，而且（内存版）是 Map 的 key。
   key 一变，Map 里存的键和对象里的订单号就对不上，数据自相矛盾。
   （数据库版同理：id 是 UNIQUE 主键，不允许改）

Q3 为什么创建订单抛异常、支付失败返回 false？
   创建失败是"调用方给错了数据"（不该发生）-> 抛异常逼它改；
   支付失败是"正常可预期的业务结果"（订单不存在/已支付）-> 返回 false 让调用方处理。

Q4 怎么保证订单号不重复？
   先在业务层 contains(id) 检查，重复就抛异常；
   数据库层再加 UNIQUE 唯一约束兜底。
   内存版不检查的后果：Map 的 put 会静默覆盖旧订单 —— 不报错，数据悄悄丢。

Q5 为什么用 Map / 为什么选 LinkedHashMap？
   Map 按订单号一步定位，List 要遍历。
   LinkedHashMap 记住插入顺序，让"查看全部"不乱序。
   （数据库版用自增 seq + ORDER BY seq 达到同样效果）

Q6 以后要换数据库，改哪些代码？
   只改 OrderRepository（外加配置文件和依赖）。
   因为 Service 持有的仓库是外面递进来的（依赖注入），它不关心仓库是内存、文件还是 MySQL。
   ★ 这个我们已经实测过：从内存 Map 换到 H2 数据库，Main / Controller / Order / OrderStatus 一行没改。

Q7 你怎么保证代码是对的？
   写了 6 个 JUnit 测试：正常创建、金额非法、订单号重复、订单号为空、支付成功、支付不存在的订单。
   而且测试真的抓到过问题：我以为重复创建的报错是"订单号已存在"，
   实际代码里带上了订单号"订单号已存在：A001"——
   这说明测试能帮你发现"你以为的行为"和"真实行为"的差异。

Q8 内存版和数据库版，修改状态有什么不同？
   内存版：get 拿到的是同一个对象引用，setStatus 直接生效；
   数据库版：get 出来的是一个副本，改完必须调 update() 显式写回数据库，
             否则数据不会变（或重启后丢失）。

Q9 REST 风格的状态码怎么选？
   200 正常 / 201 创建成功 / 400 参数不合法 / 404 资源不存在 / 409 状态冲突 / 500 服务器 bug。
   语义要分清：400 是"你请求有毛病"，404 是"东西不存在"，409 是"状态不允许"。

Q10 什么是依赖注入？
   对象需要的依赖，不由它自己 new，而是从外面传进来（构造方法参数）。
   好处：解耦（换实现不用改代码）、可测试（能塞假对象）、
         在 Spring 里由容器统一创建和组装。

十三、并发安全（"先查后改"陷阱）
============================================================

【13.1 问题：先查后改有时间窗口】

  危险写法：
      Order order = repository.get(id);                    // ① 查
      if (order.getStatus() != UNPAID) return false;       // ② 判断（在 Java 里）
      order.setStatus(PAID);
      repository.update(order);                            // ③ 改

  ① 和 ③ 是两条独立 SQL，中间隔着一段时间。这段时间里数据库可能已被别人改过。

  两个请求同时支付同一笔订单：
      请求A: 查到 UNPAID
      请求B:              查到 UNPAID
      请求A: 判断通过 -> 改成 PAID -> 保存 -> 返回"成功"
      请求B:                          判断也通过 -> 改成 PAID -> 保存 -> 返回"成功"
    结果：同一笔订单被"支付成功"两次。

  ★ 实测（20 线程并发支付同一订单，用旧的"先查后改"写法）：
      成功次数 = 17 次！   （不是 1 次）
    这种 bug 平时测试很容易漏掉，因为它是"时序相关"的 ——
    两个请求错开一点点就没事，上线半年可能都不出现，一出现就是资金问题。

【13.2 修复：把判断条件写进 SQL 的 WHERE】

  "检查"放在哪里，决定了它安不安全：

      放在 Java 里（if 判断）  -> ❌ 检查和修改之间有窗口期
      放在 SQL 的 WHERE 里     -> ✅ 检查和修改在同一个原子操作内

  修复后的 SQL：
      -- 修改前：无条件改
      UPDATE orders SET status = ? WHERE id = ?

      -- 修改后：改的时候顺便检查状态
      UPDATE orders SET status = ? WHERE id = ? AND status = 'UNPAID'

  数据库执行单条 SQL 是【原子】的 —— 要么全部生效，要么完全不生效，不会被插队。
  两个请求必然排队：先到的改成功（rows=1），后到的发现条件不满足（rows=0）。

【13.3 靠"受影响行数"判断成败】

  jdbc.update(...) 返回被修改的行数：

      int rows = jdbc.update(
              "UPDATE orders SET status = ? WHERE id = ? AND status = ?",
              newStatus.name(), id, OrderStatus.UNPAID.name());
      return rows == 1;

      rows == 1  -> 我改到了，说明订单存在且当时还是 UNPAID -> 我抢到了，成功
      rows == 0  -> 一行都没改到 -> 订单不存在，或已被别人改了 -> 失败

  好处：不需要额外查询、不需要加锁、不需要 synchronized，
        一条 SQL 同时完成"检查 + 修改 + 判断结果"。

【13.4 Service 层随之简化】

  修复前（11 行，且 pay / cancel 几乎重复）：
      public boolean pay(String id) {
          Order order = repository.get(id);
          if (order == null) return false;
          if (order.getStatus() != OrderStatus.UNPAID) return false;
          order.setStatus(OrderStatus.PAID);
          repository.update(order);
          return true;
      }

  修复后（1 行，pay / cancel 共用同一个数据层方法）：
      public boolean pay(String id) {
          return repository.updateStatusIfUnpaid(id, OrderStatus.PAID);
      }

      public boolean cancel(String id) {
          return repository.updateStatusIfUnpaid(id, OrderStatus.CANCELLED);
      }

  原来的三件事（查存在、查状态、改状态）合并成一条 SQL。
  附带好处：少一次查询、消除重复代码。

【13.5 同一模式的通用场景（面试加分）】

  凡是"检查某个条件，然后基于该条件做修改"都要考虑并发，写法都一样：

      扣库存（不会超卖）：
          UPDATE product SET stock = stock - 1 WHERE id = ? AND stock > 0

      转账扣款（余额不足就扣不动）：
          UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?

      领优惠券 / 抢红包：同理，把"还有余量"写进 WHERE

【13.6 怎么测并发（CountDownLatch 发令枪）】

  关键：要让线程【同时】冲，而不是依次调用。用 CountDownLatch 当发令枪：

      CountDownLatch startGate = new CountDownLatch(1);   // 发令枪
      // 所有线程先 startGate.await() 集合等待
      // 主线程 startGate.countDown() 一声令下，20 个线程同时冲
      assertEquals(1, successCount.get());                // 只能有 1 个成功

  注意点：
      - 计数要用 AtomicInteger（普通 int++ 不是线程安全的）
      - 断言"恰好 1 个成功"，而不是"至少 1 个"—— 后者测不出重复支付

  实测（修复后，20 线程并发支付）：
      单元测试：Tests run: 8, Failures: 0
      HTTP 端到端：HTTP 200 出现 1 次，HTTP 409 出现 19 次  ✅

【13.7 什么时候需要事务 @Transactional】

  事务 = 一组操作"要么全成功，要么全失败"（ACID 里的 A：原子性）。
  Spring 的 @Transactional：方法内抛异常 -> 自动回滚。

  什么时候需要？
      当一次业务操作包含【多条】写操作时。
      例如：支付 = 改订单状态 + 插支付流水 + 更新统计表
            如果第 2 步失败，没有事务就会留下"订单已支付但没有流水"的脏数据。

      反之：只有一条写操作时，单条 SQL 本身就是原子的，不需要显式事务。

  ★ 能答出"什么时候不需要事务"，比只会说"我会加 @Transactional"更显成熟。

【13.8 同类问题："先查后插"也一样有窗口期】

  修好 pay/cancel 之后要注意：【创建订单也有同样的问题】。

      if (repository.contains(id)) {                    // ① 查：不存在
          throw new IllegalArgumentException("订单号已存在：" + id);
      }
      Order order = new Order(id, amount, UNPAID);
      repository.add(order);                            // ② 插：可能撞唯一约束

  ① 和 ② 之间，别的请求可能已经插进去了 —— 后到的会撞上数据库的 UNIQUE 约束。

  实测（20 个并发创建同一订单号）：
      创建成功           = 1
      友好业务错误(400)  = 0
      数据库异常(→500)   = 19    ← 19 个请求返回了 500！

  ★ 危害：用户看到 500 会以为"系统坏了"，其实只是"订单号重复"——
    一个可预期的业务结果，被当成了服务器故障。

  修法：把数据库异常【翻译】成同样的业务错误：

      try {
          repository.add(order);
      } catch (DuplicateKeyException e) {          // Spring 对"唯一约束冲突"的封装
          throw new IllegalArgumentException("订单号已存在：" + id);
      }

  修复后实测：201 出现 1 次，400 出现 19 次，500 出现 0 次。

  ★ 通用思路（值得记住）：
    凡是"先查再写"的地方，都要问一句"查完之后、写之前，条件可能变吗？"
    变了就两种兜法：
      a) 把条件写进 SQL 的 WHERE（如 UPDATE ... WHERE status = 'UNPAID'）
      b) 让数据库约束兜底，再把这个异常【翻译】成友好错误
    修了一处并发问题后，要主动检查【同类写法】还有没有别的地方 —— 这叫举一反三。


============================================================
十四、从 H2 迁移到 MySQL（Profile / Docker / 连接池）
============================================================

【14.1 为什么要换】
  H2 是"学习/测试库"的印象；真实项目用 MySQL / PostgreSQL。
  换库也能再次验证"分层的价值"—— 这次只改了配置和依赖，
  OrderController / OrderService / Order / OrderStatus 一行没动。

【14.2 要改的东西（比想象的少）】
  pom.xml                  加 mysql-connector-j（版本由 Spring Boot 父 POM 管理，不用写 version）
  application.properties   数据源 URL / 驱动 / 账号
  （schema.sql 不用改，见 14.5）

  驱动依赖用 <scope>runtime</scope>：代码里从不 import 任何 MySQL 的类，
  驱动是运行时由 JDBC 按 driver-class-name 反射加载的。

【14.3 Profile：多环境配置】
  问题：开发要连 MySQL，测试要用内存库，不能改来改去。

  Spring Boot 的约定：
      application.properties          公共配置（所有环境生效）
      application-<profile>.properties 该 profile 专属配置
      激活方式：mvn spring-boot:run -Dspring-boot.run.profiles=h2

  ★ 优先级：profile 专属文件 > 公共文件（同名 key 以 profile 为准）
    —— 所以 application-h2.properties 里写同名 key 就能"覆盖"掉 MySQL 的连接信息。

  本项目三个配置文件的职责：
      application.properties            公共 + 默认数据源 = MySQL
      application-h2.properties         h2 profile：改用 H2 文件库（免 Docker）
      src/test/resources/application.properties   测试：H2 内存库

  ★ 为什么测试不需要 MySQL？（重要）
    Maven 把 src/test/resources 复制到 target/test-classes，
    测试时它在 classpath 上【排在 target/classes 之前】。
    Spring 按文件名找 application.properties，取到的第一个就是测试那份，
    主配置里的 MySQL 连接信息在测试中【根本不会被加载】。
    所以跑测试不需要 Docker、不需要数据库，几秒完成。

【14.4 连接池（HikariCP）】
  为什么需要？
    建立数据库连接很贵（TCP 握手 + 认证）。如果每个请求都新建一条，
    并发一高就把数据库连接数用光（MySQL 默认 max_connections=151）。
    连接池 = 预先建好一批连接反复复用。

  Spring Boot 自带 HikariCP，加 spring-boot-starter-jdbc 就有，无需额外依赖。
  常用配置：
      spring.datasource.hikari.maximum-pool-size=10      池中最多几个连接
      spring.datasource.hikari.minimum-idle=2            空闲时至少保留几个
      spring.datasource.hikari.connection-timeout=30000  取连接最长等待（毫秒），超时抛异常
      spring.datasource.hikari.pool-name=OrderHikariPool 给池取名字，日志里好认

【14.5 schema.sql 要能同时适配 H2 和 MySQL】
  两边方言有差别，写"交集"就行：
    - 不要用 MySQL 的反引号 `col`（H2 不认）
    - 不要用保留字做列名
    - BIGINT AUTO_INCREMENT PRIMARY KEY / DECIMAL(12,2) / VARCHAR(n) —— 两边都支持
  这样一份 schema.sql 就能同时服务 MySQL 与 H2。

【14.6 MySQL 连接 URL 的参数（每个都有原因）】
  jdbc:mysql://localhost:3306/orderdb
      ?useUnicode=true&characterEncoding=utf8   UTF-8 传输，中文不乱码
      &serverTimezone=Asia/Shanghai             明确时区，否则驱动可能报错
      &useSSL=false                             本地开发不走 SSL（生产要开）
      &allowPublicKeyRetrieval=true             MySQL 8 默认 caching_sha2_password 插件，
                                                非 SSL 连接下需要允许取公钥才能握手成功

【14.7 Docker Compose：一键起数据库】
  为什么用 Compose？
    不用在每台机器上手动装 MySQL、手动建库建账号；
    一份 docker-compose.yml 描述环境，换机器 / 给同事 / 上 CI 都一样。

  services:
    mysql:
      image: mysql:8.4
      environment:
        MYSQL_ROOT_PASSWORD: root123     # root 仅管理用
        MYSQL_DATABASE: orderdb          # 首次启动自动建库
        MYSQL_USER: order                # 自动建应用账号
        MYSQL_PASSWORD: order123
      ports: ["3306:3306"]               # 宿主机:容器
      volumes: [mysql-data:/var/lib/mysql]   # 具名卷：容器删了数据还在
      healthcheck:
        test: ["CMD","mysqladmin","ping","-h","127.0.0.1","-u","root","-proot123"]
        interval: 5s
        retries: 20
        start_period: 30s
  volumes:
    mysql-data:

  ★ 健康检查（healthcheck）为什么必要？
    容器"起来了"不等于数据库"能用了"—— MySQL 首次启动要初始化几十秒，
    这期间连接会失败。healthcheck 让 docker 知道什么时候真正可用
    （docker compose ps 会显示 healthy）。

  ★ 具名数据卷（volumes）为什么重要？
    不写 volumes 的话，docker compose down 时容器里的数据一起没了。
    写了具名卷，容器删了数据还在，下次 up 又挂回来。
    想彻底清空数据：docker compose down -v

  ★ 常用命令：
    docker compose up -d         启动（后台）
    docker compose ps            看状态（应有 healthy）
    docker compose logs -f mysql 看日志
    docker compose stop          停止（保留数据）
    docker compose down          停并删容器（保留数据卷）
    docker compose down -v       连数据卷一起删（清空数据）

  ★ 不要写 version: '3' —— Compose V2 已废弃该字段，写了会告警。

  ★ 安全提醒：这些明文口令只是【开发环境】用。
    生产环境要把口令放到环境变量 / 配置中心，绝不能进代码库。

【14.8 ★★ 踩到的坑：.properties 文件不支持行尾注释！】

  我写了这样的配置，结果应用启动直接崩：

      spring.datasource.hikari.connection-timeout=30000  # 取连接的最长等待时间

  报错：
      Failed to bind properties under 'spring.datasource.hikari.connection-timeout' to long:
      Value: "30000  # 取连接的最长等待时间"

  ★ 原因：.properties 格式里，# 或 ! 【只有出现在行首】才是注释。
    写在 = 后面的会被当成【值的一部分】。于是 "30000  # 说明文字" 转换 long 失败。

  ★ 正确写法：注释单独占一行

      # 取连接的最长等待时间（毫秒）
      spring.datasource.hikari.connection-timeout=30000

  ★ 这也再次说明：改完一定要【真的启动一次】。
    光看配置文件"感觉对"，是发现不了这类问题的。

【14.9 迁移的排查思路（这次就是这么定位的）】
  启动报错时，从报错内容能判断卡在哪一步：
    "Communications link failure"        -> TCP/端口/防火墙 不通
    "Access denied for user 'x'@'y'"     -> 已连上 MySQL，只是账号/密码不对
    "Unknown database 'xxx'"             -> 账号通了，但库不存在
  本项目启动时得到的是 "Access denied"，
  说明驱动、地址、端口、连接池【全都对】，只差建库建账号。

【14.10 MySQL 端到端验证结果（真机跑过）】

  验证方法：用本机已装的 MySQL 8.1 二进制，另起一个【独立的临时实例】（3307 端口），
  不动原有的 3306 实例、不需要管理员权限、不需要 Docker。

  步骤（这个技巧很实用）：
    # 1) 初始化一个全新数据目录（root 空密码）
    mysqld --initialize-insecure --basedir="<MySQL目录>" --datadir="<空目录>"
    # 2) 用非默认端口启动（避开已被占用的 3306）
    mysqld --basedir=... --datadir=... --port=3307 --bind-address=127.0.0.1 --mysqlx=OFF
    # 3) 建库建号
    mysql -h 127.0.0.1 -P 3307 -u root -e "CREATE DATABASE orderdb ...; CREATE USER ..."
    # 4) 应用用【环境变量】覆盖数据源地址（不改已提交的配置文件）
    $env:SPRING_DATASOURCE_URL = "jdbc:mysql://127.0.0.1:3307/orderdb?..."
    mvn spring-boot:run

  ★ 用环境变量覆盖配置：Spring Boot 的 relaxed binding —— 
    环境变量 SPRING_DATASOURCE_URL 会自动映射到 spring.datasource.url，
    且【环境变量优先级高于配置文件】。适合临时验证、不适合写进代码库。

  验证结果（全部通过）：
    - 启动日志出现 "OrderHikariPool - Added connection com.mysql.cj.jdbc.ConnectionImpl"
      -> 证明真的建了 MySQL 连接（不是 H2）
    - 创建 / 分页 / 校验 / 支付 / 重复支付(409) / 统计 全部正常
    - 金额小数（199.99、0.01）精确无误
    - 应用停止后直接查 MySQL：数据仍在
    - 重启应用：数据完好、状态未丢（MYSQL-01 仍是 PAID）-> 真持久化
    - 20 并发支付同一订单：1 成功 + 19 冲突；20 并发取消同理
      -> 说明"原子条件更新（UPDATE ... WHERE status=?）"在 MySQL 上同样并发安全

【14.11 测试踩到的一个"假故障"：PowerShell 传 URL 参数】

  现象：curl 请求 "http://localhost:8080/orders?page=1&size=2" 返回空，看起来像 bug。
  原因：PowerShell 把含 & 的参数传给【原生 exe】时会被吃掉/截断（& 在 PowerShell 里是特殊字符）。
  解决：改用显式写法之一
      curl.exe -s --url "http://localhost:8080/orders?page=1&size=2"
      curl.exe -s --get --data-urlencode "page=1" --data-urlencode "size=2" "http://localhost:8080/orders"

  ★ 教训：验证时结果反常，先怀疑【测试工具/命令行】，再怀疑代码。
    判断方法：换个调用方式再试一次 —— 换了就对，说明问题在测试手法，不在代码。

【14.12 容器化：Dockerfile 多阶段构建 + compose 加 app 服务】

  之前只有数据库是容器，应用还得在宿主机 mvn spring-boot:run。
  补上 Dockerfile 之后才叫"一条命令起全套"：
      docker compose up -d --build

  ★ 多阶段构建（Multi-stage build）

      # 阶段 1：编译打包
      FROM maven:3.9-eclipse-temurin-21 AS build
      WORKDIR /build
      COPY pom.xml .
      RUN mvn -B -q dependency:go-offline
      COPY src ./src
      RUN mvn -B -q clean package -DskipTests

      # 阶段 2：运行（只拿到阶段 1 的 jar）
      FROM eclipse-temurin:21-jre
      WORKDIR /app
      RUN useradd --system --uid 1001 --create-home appuser
      COPY --from=build --chown=appuser:appuser /build/target/*.jar app.jar
      USER appuser
      EXPOSE 8080
      ENTRYPOINT ["java", "-jar", "/app/app.jar"]

    为什么必须分阶段？
      直接用 maven 镜像当运行环境 -> 镜像里带着 Maven、整个 ~/.m2、甚至源码，
      700MB 以上，而且把构建工具暴露在运行环境里（攻击面变大）。
      分阶段后最终镜像 = JRE + 一个 jar，本项目 CI 实测 352MB。
      关键就是那句 COPY --from=build：只把产物拿过来，别的全丢。

  ★★ 层缓存顺序（很容易忽略的性能点）

      Docker 每个指令是一层，某一层的输入变了，它【以及之后所有层】都失效重建。
      源码天天改、pom.xml 很少改，所以：
          先 COPY pom.xml + dependency:go-offline   -> 依赖这层能一直命中缓存
          再 COPY src                               -> 改代码只重建后面几层
      反过来写（先 COPY . 再 mvn）：
          改一行代码 -> 全部缓存失效 -> 每次重新下载几百 MB 依赖。

  ★ 两个容器安全/运维细节

      1) 不用 root 运行：USER appuser
         容器被突破时，root 的危害远大于普通用户。这是容器安全基线的常见检查项。

      2) ENTRYPOINT 必须用 exec 形式（JSON 数组）
            ✅ ENTRYPOINT ["java", "-jar", "/app/app.jar"]
            ❌ ENTRYPOINT java -jar /app/app.jar     <- 会被包成 sh -c "..."
         shell 形式下 java 不是 1 号进程，收不到 docker stop 发的 SIGTERM，
         只能等 10 秒后被 SIGKILL 强杀 —— Spring 的优雅停机（关连接池、处理完在途请求）就失效。

         要调 JVM 参数不要改 ENTRYPOINT，用 JAVA_TOOL_OPTIONS：
             environment:
               JAVA_TOOL_OPTIONS: "-XX:MaxRAMPercentage=75"
         JVM 会自动读取这个环境变量（启动日志里会打印 "Picked up JAVA_TOOL_OPTIONS: ..."）。
         好处：同一个镜像能在不同环境跑不同参数，不用重新构建。

  ★ .dockerignore：控制"什么不进构建上下文"

      docker build 会先把整个目录打包发给 Docker 引擎，这个包叫 build context。
      target/（30MB+ jar）、data/（数据库文件）、.git/（全部历史）都需要排除，
      否则传输和构建都会变慢。

  ★★★ 最大的坑：容器里的 localhost 是【容器自己】

      application.properties 里写的是 localhost:3306（宿主机上跑没问题），
      但放进 app 容器后，localhost 指向 app 容器自身 —— 那里没有 MySQL。
      容器之间必须用【compose 的服务名】互相访问：
          jdbc:mysql://mysql:3306/orderdb?...       <- mysql 是服务名
      Docker 内置 DNS 会把服务名解析到对应容器的 IP。

      做法上不改一行代码，用环境变量覆盖（和 CI 里切 MySQL 是同一招）：
          environment:
            SPRING_DATASOURCE_URL: "jdbc:mysql://mysql:3306/orderdb?..."

  ★ 启动顺序：depends_on 的两种写法差别巨大

      depends_on: [mysql]                                  只等"容器启动"
      depends_on: {mysql: {condition: service_healthy}}    等健康检查通过（本项目用这个）

      用前者最常见的事故：MySQL 还在初始化数据目录，app 已经启动并连接失败退出，
      重启几次才勉强起来 —— 看起来像"偶发 bug"，其实是时序问题。
      （和 CI 里配 --health-cmd 是同一个道理。）

  ★ 端口映射

      ports: ["8080:8080"]     宿主机:容器
      mysql 的 "3306:3306" 是为了让宿主机上的客户端/Workbench 能连；
      如果宿主机 3306 已被占用，改成 "3307:3306" 即可，容器网络内部仍然用 3306。

  ★ 没有 Docker 时怎么验证？（本次就是这样）

      docker build 无法执行时，可以验证"容器启动时真正依赖的东西"：
        1) mvn -B -q dependency:go-offline           确认 Dockerfile 里这行能跑通
        2) mvn clean verify                          确认产物是 fat jar
        3) 用 compose 里【同样的环境变量】直接跑 jar：
             $env:SPRING_DATASOURCE_URL = "jdbc:mysql://127.0.0.1:3307/orderdb?..."
             $env:JAVA_TOOL_OPTIONS = "-XX:MaxRAMPercentage=75"
             java -jar target/order-app-1.0.0.jar
           日志里应出现 "Picked up JAVA_TOOL_OPTIONS" 和
           "OrderHikariPool - Added connection com.mysql.cj.jdbc.ConnectionImpl"
        4) 请求接口并直接查库，确认数据真的落盘
      验证不到的部分只剩【镜像层】：严格来说仍需要 docker build 一次才算完全确认。

  ★ 面试话术
      "应用用多阶段构建：maven 镜像里编译打包，只把 jar 复制到 jre 镜像运行，
       最终镜像不含构建工具和依赖缓存。Dockerfile 里把 COPY pom.xml 放在 COPY src 之前，
       配合 dependency:go-offline 让依赖层能命中缓存，改代码不会重新下依赖。
       运行时用非 root 用户，ENTRYPOINT 用 exec 形式保证能收到 SIGTERM 做优雅停机。
       compose 里 app 通过服务名连 mysql，并用 depends_on 的 service_healthy
       等数据库就绪，避免启动时序导致的连接失败。"


============================================================
十五、订单明细（1:N）与事务
============================================================

【15.1 为什么要做 1:N】
  之前的订单只有一个"总金额"，等于"一笔订单 = 一个数"。
  真实订单是"一笔订单 = 若干商品"，所以拆成两张表：

      orders        1  ----  N  order_items
      (订单)                     (明细：商品名/单价/数量)

  这叫【一对多关系】。数据库里用【外键】表达：
      order_items.order_id -> orders.id

【15.2 建表要点】
  CREATE TABLE IF NOT EXISTS order_items (
      seq          BIGINT AUTO_INCREMENT PRIMARY KEY,
      order_id     VARCHAR(64)   NOT NULL,
      product_name VARCHAR(128)  NOT NULL,
      price        DECIMAL(12,2) NOT NULL,
      quantity     INT           NOT NULL,
      CONSTRAINT fk_order_items_order
          FOREIGN KEY (order_id) REFERENCES orders (id)
  );

  ★ 三个细节：
    1) 外键保证"明细一定属于一张存在的订单"，插入不存在的订单号会被拒绝。
    2) 外键列【自动建索引】：MySQL 和 H2 都会为外键列建索引，
       所以按 order_id 查明细不会全表扫描，不需要手写 CREATE INDEX
       （而且 MySQL 8 不支持 CREATE INDEX IF NOT EXISTS，写了反而两边不通用）。
    3) 被外键引用的列必须有唯一约束 —— orders.id 上的 UNIQUE 正好满足。

  ★ 删除顺序：有外键时，必须先删明细、再删订单。
    测试里清库就踩到了：DELETE FROM orders 会因外键约束失败。

【15.3 ★★ 事务：为什么这次真的需要 @Transactional】

  创建订单 = 写两张表：
      1. INSERT INTO orders ...
      2. INSERT INTO order_items ...（可能多条）

  如果第 1 步成功、第 2 步失败（比如商品名太长被数据库拒绝），
  数据库里就会留下一张【没有明细的订单】—— 金额 15.00，打开却没有任何商品。
  这种"半截数据"叫脏数据，比直接失败还糟糕，因为没人会注意到。

  @Transactional 的语义：把方法内的所有写操作看成【一个整体】，
  方法抛出运行时异常 -> 全部回滚，数据回到方法执行前的样子。

      @Transactional
      public Order createOrder(String id, BigDecimal amount, List<OrderItem> items) { ... }

  ★ 只有【运行时异常】（RuntimeException / Error）默认触发回滚；
    受检异常（checked exception）默认【不回滚】—— 需要写 @Transactional(rollbackFor = Exception.class)。

  ★ 实测验证（本项目真的演示过）：
    把 @Transactional 注释掉再跑回滚测试，测试立刻失败：
        expected: <null>
        but was:  <A001 | 金额 15.00 | 状态 UNPAID>
    订单留下了、明细回滚了 —— 正是脏数据。
    加回注解后测试通过。这比"看文档记住"要牢得多。

【15.4 ★ @Transactional 的经典坑：自调用失效】

  Spring 的事务是靠【代理对象】实现的：外部调用 -> 代理 -> 开启事务 -> 真实方法。
  如果在同一个类里直接调用另一个方法：

      public Order a() { return b(); }        // 直接 new 出来的 this.b()，没经过代理
      @Transactional public Order b() { ... } // b 上的事务【不生效】

  解决：
    - 两个入口方法都加注解（本项目就是这么做的）
    - 或者把 B 挪到另一个 Bean 里
    - 或者注入自己（不推荐）

  ★ 另外：@Transactional 加在 private 方法上无效（代理无法拦截）。

【15.5 ★★ 金额必须由服务端计算（安全）】

  客户端能传的只有：商品名、单价、数量。
  小计和总价一律由服务端算：

      subtotal = price × quantity
      total    = Σ subtotal

  为什么？如果让客户端传"总价"，客户端把 1000 元改成 1 元就能付款成功。
  这和"前端校验不能代替后端校验"是同一个道理：
  凡是【客户端能改的数据】，都不能直接当成事实。

  本项目实测：请求里同时传 amount=1.00 和两条明细，
  返回的金额仍然是服务端算出的 23.50。

【15.6 ★ N+1 查询问题：列表为什么不返回明细】

  假设列表接口返回 10 条订单，且每条都要带明细：
      1 次查询取订单 + 10 次查询取明细 = 11 次数据库往返
  这就是 N+1 问题（1 次主查询 + N 次从查询），数据量大时会把数据库拖垮。

  本项目的做法：
      GET /orders        -> OrderResponse（不含明细）
      GET /orders/{id}   -> OrderDetailResponse（含明细，只查 1 次）

  ★ 面试延伸：如果确实需要在列表里带关联数据，可以用
    联表查询（JOIN）、批量查询（IN 一次查完再在内存里分组）、
    或 ORM 的 fetch join / @EntityGraph 来避免 N+1。

【15.7 实体为什么不在 Order 里放 List<OrderItem>】
  三个原因：
    1) 会诱发 N+1（见 15.6）
    2) 明细只在详情页需要，按需查询更省资源
    3) 实体互相持有容易形成循环引用，JSON 序列化时会无限递归

  需要明细时，由 Service 显式调用 repository.findItems(orderId)。

【15.8 批量插入：batchUpdate】
  jdbc.batchUpdate("INSERT INTO order_items (...) VALUES (?,?,?,?)", List<Object[]>);

  为什么不用 for 循环单条 insert？
    循环 = n 次"应用 -> 数据库"网络往返；batchUpdate 会攒成一批发送，
    由驱动/数据库一次处理，明细多时差距非常明显。

【15.9 DTO 的分裂：列表 DTO vs 详情 DTO】
  OrderResponse       : id / amount / status
  OrderDetailResponse : id / amount / status / items[]

  这不是重复代码，而是【按场景裁剪契约】：
  列表接口不承诺返回明细，详情接口才承诺。
  好处是列表性能可控，而且以后详情再加字段不会影响列表接口。


============================================================
十六、认证（Authentication）与授权（Authorization）
============================================================

【16.1 两个词必须分清】

  认证 Authentication —— "你是谁？"        证明身份     登录 + JWT 验签
  授权 Authorization  —— "你能干什么？"    决定权限     订单 owner_id 过滤

  ★ 只有认证不够：能登录 ≠ 能看所有人的订单。

【16.2 密码怎么存（三种错误 + 一种正确）】

  ❌ 明文存储            数据库泄露 = 密码全泄露
  ❌ MD5 / SHA-256       没有盐，彩虹表可反查；且"快"正适合暴力破解
  ❌ 全局固定盐          同一密码哈希相同，仍可批量破解
  ✅ BCrypt              慢（可调成本因子）+ 每次随机盐

      String hash = encoder.encode(rawPassword);       // 注册
      boolean ok  = encoder.matches(rawPassword, hash);// 登录

  为什么"慢"是优点？
      MD5 每秒能算几十亿次，BCrypt 每秒只能算几千次 —— 暴力破解成本差几个数量级。
  为什么随机盐有用？
      同一密码两次 encode 结果不同，彩虹表（预先算好的哈希表）失效。
  为什么不可逆？
      拿到 $2a$10$... 推不出原文，只能"用原文再算一次比对"。

  ★ 登录失败不要区分"用户不存在"和"密码错误"
      分别提示等于告诉攻击者哪些用户名有效（用户枚举）。
      两者统一返回"用户名或密码错误"。

【16.3 JWT 结构与原理】

  三段，用 . 分隔：  header . payload . signature

      header    : {"alg":"HS256"}
      payload   : {"sub":"alice","role":"USER","exp":...}
      signature : 用【服务端密钥】对前两段做 HMAC

  ★★ 最重要的一句话：JWT 是【签名】，不是【加密】！
      payload 只是 Base64 编码，任何人都能解开看内容：
          echo "eyJzdWIiOiJhbGljZSJ9" | base64 -d   ->  {"sub":"alice"}
      所以 token 里【绝不能放密码、身份证、手机号】等敏感信息。

  那安全性从哪来？签名。
      攻击者把 payload 里的 sub 从 alice 改成 admin
      -> payload 变了 -> 签名对不上 -> 验签失败 -> 401
      除非他拿到服务端密钥，否则改不了内容。

  密钥要求：HS256 需要 >= 256 位（32 字节）。
      本项目在构造时就直接创建 SecretKey，密钥太短会启动失败 —— 这是好事，
      防止"弱密钥上线"这种问题被带进生产。

  ★ JWT vs Session
      Session：状态存在【服务端】内存/Redis，多台服务器要共享，可以主动踢人
      JWT    ：状态在【客户端】，服务端只验签（无状态），扩容简单，
               但"主动让某个 token 失效"很难（只能等过期或维护黑名单）

【16.4 一次请求的完整链路（本项目真实流程）】

      GET /orders
      Authorization: Bearer eyJhbGci...
            |
            v
      AuthInterceptor.preHandle()
        1. 有 Authorization 头吗？          没有 -> 401
        2. 是 "Bearer " 开头吗？            不是 -> 401
        3. 验签 + 检查过期                  失败 -> 401
        4. request.setAttribute("currentUsername", "alice")
            |
            v
      OrderController.list(@RequestAttribute("currentUsername") String user)
            |
            v
      service.listOrders(page, size, user)
            |
            v
      SELECT ... WHERE owner_id = 'alice' ORDER BY seq LIMIT ? OFFSET ?

  ★★ 核心原则：身份信息必须来自【服务端认证过的凭据】，
    绝不能接受客户端自称的身份（如 ?username=alice）。

【16.5 拦截器 vs 过滤器（面试常问）】

  Filter       Servlet 层，包裹所有请求，看不到 Spring 的 Controller 方法
  Interceptor  Spring MVC 层，能看到 handler（Controller 方法），能读方法上的注解，
               更适合做"接口级鉴权"

  本项目用 HandlerInterceptor，因为它足够简单且流程透明；
  真实项目常用 Spring Security 的过滤器链（功能更全：CSRF、方法级权限 @PreAuthorize 等）。

  ★ 拦截器里 return false 之后，@RestControllerAdvice 不会生效
    （异常处理是 Controller 层的事），所以 401 的 JSON 要自己写：
        response.setStatus(401);
        response.setContentType("application/json;charset=UTF-8");
        objectMapper.writeValue(response.getWriter(), Map.of("error", msg));

【16.6 状态码怎么选：401 / 403 / 404】

  401 Unauthorized  未认证：没 token / token 无效 / 已过期
  403 Forbidden     已认证但无权限（常见于"角色不够"，如非管理员访问后台）
  404 Not Found     资源不存在

  ★ 本项目"访问别人的订单"返回 404，而不是 403：
      如果返回 403，攻击者可以通过 403/404 的差异判断哪些订单号存在（订单号枚举）。
      统一 404 = 不泄露"资源是否存在"。

【16.7 数据隔离要落在 SQL 里】

  ❌ 查全部再内存过滤：
        repository.listAll().stream().filter(o -> user.equals(o.getOwnerId()))
     10 万条订单 = 把 10 万条读进内存，慢且可能 OOM
  ✅ 数据库过滤：
        SELECT ... FROM orders WHERE owner_id = ? ORDER BY seq LIMIT ? OFFSET ?

  ★ 和"真分页 vs 假分页"是同一个道理：能在数据库做的，不要拉到应用层做。

【16.8 测试策略：加一个开关】

  两类测试：
      OrderServiceTest / OrderControllerTest  -> app.auth.enabled=false（专注业务）
      AuthApiTest                             -> @SpringBootTest(properties="app.auth.enabled=true")

  为什么不全部打开？
      39 个业务测试每个都要带 token，改动量大且与业务无关。
      测试原则：一个测试只验证一件事。鉴权由专门的测试类覆盖。

  ★ MockMvc 加请求头：
        mockMvc.perform(get("/orders").header("Authorization", "Bearer " + token))

【16.9 又一次踩到"测试配置完全遮蔽主配置"】

  启动报错：Could not resolve placeholder 'app.jwt.secret'
  原因：src/test/resources/application.properties 与主配置【同名】，
        它把主配置【整份遮蔽】（不是合并），所以主配置里的 app.jwt.* 在测试中读不到。
  解决：测试配置里也写一份 app.jwt.secret / app.jwt.expire-minutes。

  ★ 记住：同名配置文件"前者完全覆盖后者"，不是"两个文件合并"。

【16.10 安全清单（面试可直接背）】

  1. 密码 BCrypt 哈希            防：数据库泄露后明文密码
  2. 登录失败不区分原因          防：用户枚举
  3. JWT 只放非敏感信息          防：token 被解码后泄露隐私
  4. HS256 签名                  防：篡改 payload
  5. 身份取自 token，不取参数    防：冒充他人
  6. 他人资源返回 404            防：订单号枚举
  7. 过滤条件写进 SQL WHERE      防：越权 + 性能问题
  8. 密钥走配置、不进代码库      防：密钥泄露

【16.11 实测结果（本项目真机验证）】

  注册 alice / bob -> 各自拿到 3 段式 token
  alice 创建 A-ALICE(100.00)
      alice 列表: total=1        bob 列表: total=0
      bob 查详情: 404            bob 支付: 404
      alice 支付: 200            alice 统计 100.00 / bob 统计 0
  密码错误: 401                  篡改 token: 401
  测试总数 39 -> 50 全绿（新增 AuthApiTest 11 个）

【16.12 授权模型：角色（RBAC）与"谁能做什么"】

  认证只回答"你是谁"；授权才回答"你能做什么"。
  只有 401 的系统等于"登录即全能" —— 任何有账号的人都能看所有人的数据，
  这是学生项目最典型的安全漏洞。

  ★ 角色设计（本项目）
      USER  普通用户：只能操作自己的订单
      ADMIN 管理员：可读全部订单、可取消任意订单、可看用户列表与全局统计

    权限矩阵（写进 README，也是面试回答模板）：
      操作                 USER    ADMIN
      查自己的订单          ✅      ✅
      查别人的订单          ❌ 404  ✅（走 /admin）
      取消别人的订单        ❌ 404  ✅（走 /admin）
      支付别人的订单        ❌ 404  ❌ 不提供
      查看全部用户          ❌ 403  ✅
      全局统计              ❌ 403  ✅

    ★ 关键设计：读权限可以放宽，写权限按业务性质分级。
      管理员能审计、能止损（取消），但不能替用户花钱（代付）。
      权限是"能对谁做"，不是"能跳过业务规则"。

  ★ 三层防护，各管一段，不能互相替代
      1) 路径级（粗粒度）：/orders/** 要登录，/admin/** 要 ADMIN
                           -> 未登录 401，角色不够 403
      2) 资源级（细粒度）：这张订单是不是你的
                           -> 不是你的 404（不泄露存在性）
      3) 业务级：订单状态允不允许这个操作
                           -> 只有 UNPAID 能支付/取消，否则 409（管理员同样受约束）

      只做路径级 -> 管理员可以改任意订单状态，无法无天；
      只做资源级 -> 普通用户能调管理接口，契约已经破了。

  ★ 为什么用注解声明权限，而不是在拦截器里 if 路径
      ❌ if (uri.startsWith("/admin"))
           以后加 /report/** 时忘了改 -> 接口裸奔，而且没人会发现
      ✅ 类上标 @RequireRole(Role.ADMIN)
           权限要求和接口写在一起，review 时一眼可见；
           拦截器只负责"读注解 + 比角色"，加接口不用碰它。
      Spring Security 的 @PreAuthorize 是同一思路（本项目手写精简版，
      目的是理解原理，而不是背 API）。

  ★★ 最容易错的一步：角色从哪来

      ❌ 从 token 里读 role
          token 是签发时写死的。用户被撤职后，旧 token 里仍写着 ADMIN，
          直到过期前一直是管理员 —— 等于留了后门。
          想"强制下线"还得额外维护黑名单，复杂度陡增。

      ✅ 用 token 里的 username 回库查当前角色（本项目做法）
          每请求多一次按唯一索引的查询，换来权限【实时生效】：
            撤权      -> 下一个请求立刻 403，不用等 token 过期
            用户删除  -> 查不到 -> 401

      一句话：token 只证明【你是谁】，不决定【你能做什么】。

  ★ 角色绝不能由客户端决定
      注册接口硬编码 Role.USER。若允许请求体传 {"role":"ADMIN"}，
      任何人都能注册成管理员 —— 这叫"批量赋值 / Mass Assignment"漏洞。
      提权只能走运维手段（改数据库 / 后台审批）。

  ★ 还有一个细节：默认最小权限（fail-safe）
      Role.from(null) 与未知字符串一律降级为 USER。
      数据脏了、拼错了，宁可少给权限，也绝不能意外提权。

  ★ 实测（真机 Tomcat + H2，不是 MockMvc）

      注册 alice、root（两人都是 USER）
        root 访问 /admin/orders         -> 403 权限不足
        无 token 访问 /admin/orders     -> 401
        alice 访问 /admin/users         -> 403
        alice 访问 /orders/stats        -> 200（对照组：正常业务不受影响）

      数据库执行 UPDATE users SET role='ADMIN' WHERE username='root'
        同一个【旧 token】（payload 里的 role 仍是 USER）
          GET  /admin/orders            -> 200，看到 alice 的 A001
          GET  /admin/users             -> 200，且不含密码哈希
          POST /admin/orders/A001/cancel -> 200，状态变 CANCELLED
          POST /orders/A001/pay          -> 404（管理员也不能代付）

      数据库把 root 改回 USER
        同一个 token  GET /admin/orders -> 403（立即生效）
        同一个 token  GET /orders       -> 200（登录态还在，只是权限降级）

      测试总数 50 -> 65 全绿（新增 AdminApiTest 14 个）

  ★ 面试话术
      "我做的是 RBAC 的最小实现：USER / ADMIN 两个角色。
       路径级用 @RequireRole 注解在拦截器里统一拦截（401/403），
       资源级用 owner_id 校验、越权统一返回 404 防止枚举订单号。
       角色不放在 JWT 里，而是每个请求回库查 —— 这样撤权立即生效，
       不需要维护 token 黑名单。
       写权限我还做了业务分级：管理员可以取消他人订单（运营止损），
       但不能代付（资金操作必须本人发起）。"


============================================================
十七、定时任务（@Scheduled）：功能开发的标准套路
============================================================

【17.1 一个功能要改几个文件？取决于它跨几层】

  拿到需求先问 6 个问题，文件自然就出来了：

     1) 数据够不够？         缺字段/缺表 -> schema.sql
     2) 谁触发？             用户 -> Controller；时间 -> Job；消息 -> Consumer
     3) 规则是什么？         -> Service（用中文先写清一句话）
     4) 怎么读/写？          -> Repository（SQL）
     5) 对外长什么样？        -> dto/（XxxRequest / XxxResponse）
     6) 怎么证明对？          -> Test

  ★ 施工顺序 = 从下往上（依赖倒序），否则会被"找不到方法"追着跑：
        schema.sql -> Repository -> Service -> 入口(Controller/Job) -> Test

  ★ 改动文件数量取决于"跨几层"，不取决于难度：
       列表多一个字段        2 个（DTO + Test）
       加一个查询接口        3 个（Controller + Repository + Test）
       加一条业务规则        2 个（Service + Test）
       超时自动取消（本例）  5 个（schema + Repo + Service + Job + Test）

【17.2 本例：超时未支付订单自动取消】

  链路：
      OrderCleanupJob（@Scheduled，只管"什么时候"）
        -> OrderService.cancelExpiredOrders(expireHours)   （管"多久算超时"）
        -> OrderRepository.cancelExpired(deadline)          （管"怎么改库"）
        -> UPDATE orders SET status='CANCELLED'
           WHERE status='UNPAID' AND created_at < ?

  ★ 致命陷阱：WHERE 里漏掉 status='UNPAID'
      -> 三天前【已支付】的订单也会被改成已取消：钱收了，货不发。
      -> 定时任务批量改数据，一错就是一大片，条件必须精确到不能再精确。

  ★ 为什么规则不写在 Job 里？
      Job 里写规则 -> 想加"管理员手动触发"就得复制一遍规则 -> 早晚不一致。
      规则留在 Service -> 任何入口都能调，且测试直接测 Service（不用启动定时器）。

【17.3 @Scheduled 的五个要点】

  1) 必须在启动类（或任一 @Configuration）加 @EnableScheduling，
     否则 @Scheduled 静默失效 —— 不报错，任务永远不跑。这是最常见的坑。

  2) 方法必须 public、无参数、返回 void。
     因为它是被时钟触发的，没人给它传参；需要的配置用 @Value 注入到字段。

  3) cron 是【6 段】：秒 分 时 日 月 周
     （Linux crontab 是 5 段，从 crontab 抄 5 段到 Spring 会报错）
         0 */10 * * * *   = 每 10 分钟的第 0 秒

  4) cron 设为 "-" 可完全禁用（Scheduled.CRON_DISABLED）。
     测试配置里必须关掉，否则定时器会跟测试抢数据 -> 偶发失败（flaky test）。

  5) 时区显式指定 zone = "Asia/Shanghai"，避免服务器是 UTC 时跑错点。

【17.4 时间相关的测试：怎么"回到过去"】

  createOrder 写入的永远是 CURRENT_TIMESTAMP，
  要构造"2 天前创建的订单"，只能直接改库：

      jdbc.update("UPDATE orders SET created_at = ? WHERE id = ?",
              Timestamp.valueOf(LocalDateTime.now().minusDays(2)), "OLD");

  ★ 断言要覆盖三类数据（缺一类就可能漏 bug）：
       该被取消的            未支付 + 超时
       不该取消：时间不到     未支付 + 未超时
       不该取消：状态不对     【已支付】+ 超时

【17.5 ★★ 亲手验证"测试到底能不能抓 bug"】

  做法：故意把 SQL 的 status='UNPAID' 删掉，再跑测试。

  结果（真实）：
      cancelExpired_cancelsExpiredUnpaidOnly   -> 仍然全绿   （抓不到）
      cancelExpired_doesNotTouchPaidOrders     -> 变红
          expected: <0> but was: <1>   已支付的订单不该被取消

  ★ 结论：一个测试能否抓 bug，取决于它的【数据】是否踩到 bug 的触发条件。
    只测"正常路径"的测试，对"条件写漏"这类 bug 完全免疫。

  ★ 破坏性验证的方法论：
     要制造【能跑通、但结果错】的 bug，而不是【直接崩溃】。
     - 第一次我删了个 ? 但参数还是 3 个 -> 报 parameterIndex 错（崩溃），
       这验证不了测试的业务价值，只验证了"参数个数错会报错"。
     - 第二次改成 2 个参数、只按时间筛 -> 静默错误 -> 才真正验证了边界用例的价值。

【17.6 另一个坑：Java 目录必须和 package 一致】

  症状：把 OrderCleanupJob.java 建在 src/main/java/com/example/ 下，
        文件内写 package com.example.order; -> 编译失败。
  原因：package 声明就是类的全名，编译器按目录找文件。
  解法：文件必须放在 .../com/example/order/ 目录下。

【17.7 还有一个坑：改了脚本 ≠ 数据库变了】

  现象：schema.sql 里加了 created_at，查库却没有这一列。
  诊断：比对两个时间
      schema.sql 的 LastWriteTime          = 19:34:32
      应用进程的 StartTime                 = 19:29:13   <- 启动早于修改
  结论：应用读的是启动那一刻的脚本，库在 19:29 就按旧结构建好了。
  解法：停应用 -> 删 data/orderdb.mv.db -> 重启（schema.sql 会重新执行）。

  ★ 通用判据：只要"启动时间"早于"文件修改时间"，改动一定没生效。
    对 schema.sql / application.properties / Dockerfile / yml 全都成立。

【17.8 面试话术】

  "超时订单清理我做成定时任务，但 Job 里只有一行调用 Service —— 规则全部在 Service，
   所以定时触发、以后的管理端手动触发共用同一份逻辑，测试也直接测 Service 不用启定时器。
   判断条件我写成一条批量 UPDATE：WHERE status='UNPAID' AND created_at < ?，
   条件放在 SQL 里而不是查出来再筛，既少往返也避免并发窗口。
   这里我专门写了'已支付订单即使超时也不能被取消'的测试 ——
   我故意把 status 条件删掉验证过：只有这个用例会红，只测未支付的用例抓不到这个 bug。"
