一、项目全景：分层架构
============================================================

【一句话】每层只干一件事，依赖箭头只能向下。

  用户（浏览器 / 键盘）
        |
        v
  界面层  Main.java（控制台） / OrderController.java（Web）
        |        只负责：读输入、显示结果；不做任何业务判断
        v
  业务层  OrderService.java
        |        只负责：业务规则（订单号不重复、金额>0、状态流转）
        v
  数据层  OrderRepository.java
        |        只负责：订单怎么存、怎么取（Map -> 数据库）
        v
  实体    Order.java（一笔订单长什么样）
          OrderStatus.java（状态只能有哪几种取值）

【各文件职责】
  OrderStatus.java ... 枚举，定义状态取值：UNPAID / PAID / CANCELLED
  Order.java ......... 实体，3 个字段 + 构造方法 + getter + setStatus + toString
  OrderRepository.java 数据层，add / update / get / listAll / contains / size
  OrderService.java .. 业务层，createOrder / findOrder / listOrders / pay / cancel / sumAmount
  Main.java .......... 控制台入口，菜单 + Scanner 读输入
  OrderAppApplication.java  Web 入口，@SpringBootApplication
  OrderController.java  Web 接口层，把 HTTP 请求翻译成 service 调用
  ApiExceptionHandler.java  全局异常处理，Java 异常 -> HTTP 400 + JSON

【最核心的一句话】
  Main / OrderController 里【一个业务判断都没有】。
  规则全在 OrderService —— 改规则只动一个文件。
  这就是为什么不用把代码全塞进一个文件里。

【分层的回报（实测）】
  把 Map 换成 H2 数据库时，只改了 OrderRepository（+pay/cancel 写回一句），
  Main、OrderController、OrderStatus、Order 都没动。


============================================================
二、Java 基础知识点
============================================================

【2.1 枚举 enum】
  public enum OrderStatus { UNPAID, PAID, CANCELLED }

  为什么不用字符串 "未支付" 或数字 0/1/2？
    - 字符串拼错（"未支符"）编译器不报错，运行时才炸
    - 数字可读性差
    - 枚举是【类型安全】的：写错编译期就报错，IDE 还能自动补全
  命名习惯：枚举常量全大写。

【2.2 封装：private / final / getter / setter】
  private = 不给你看（外部拿不到字段）
  final   = 不给你改（只能赋一次值，可在声明时或构造方法里赋值）

  final 的效果：别人写 order.amount = 99999; 会【编译期报错】，
  等于把"不许改"交给编译器拦，而不是指望大家自觉。

  口诀：订单号、金额是"刻在石头上"的事实 -> 加 final
        状态是"白板上的字" -> 不加 final

  如果给 status 也加 final：
    setStatus 方法体里 `this.status = status;` 编译不过 -> "支付"功能写代码阶段就废了

  getter / setter（访问器）：
    getter：public 类型 getXxx() { return 字段; }
    setter：public void setXxx(类型 参数) { this.字段 = 参数; }
    （boolean 字段用 isXxx()）

  为什么要它俩？不能直接 public String id; 吗？
    能，但等于把字段敞开摆在大街上：谁都能随手改，业务规则没地方拦。
    有了 getter/setter，字段还是私有，但开了两扇"有门的通道"，门可以装锁：

      public void setAmount(int amount) {
          if (amount <= 0) throw new IllegalArgumentException("金额必须大于 0");
          this.amount = amount;
      }

  this 是什么？参数名和字段名重名时，this.字段 明确指"这个对象的字段"。

  ★【有没有 setter】本身就在表达设计意图：
      id 没 setter      -> 身份不能变
      amount 没 setter  -> 事实不能变
      status 有 setStatus -> 因为状态本来就要变
    开放得不多不少，刚刚好。

【2.3 构造方法】
  public Order(String id, int amount, OrderStatus status) {
      this.id = id; this.amount = amount; this.status = status;
  }
  作用：创建对象时一次性把字段填好。final 字段必须在这里（或声明时）赋值。

【2.4 toString 与 @Override】
  System.out.println(order) 会自动调用对象的 toString()。
  不重写 -> 打印 Order@1b6d3586（类名@十六进制），人看不懂
  重写后 -> A001 | 金额 100 | 状态 UNPAID
  口诀：println 打印什么由 toString() 决定；不写，就只给你一串"身份证号"。
  重写时加 @Override（让编译器帮你检查方法签名有没有写错）。

【2.5 异常：throw 和 try/catch】
  抛出： throw new IllegalArgumentException("金额必须大于 0");
  接住：
      try {
          int amount = Integer.parseInt(amountText);   // "100" -> 100
          Order order = service.createOrder(id, amount);
      } catch (NumberFormatException e) {              // 不是数字
          System.out.println("金额必须是数字");
      } catch (IllegalArgumentException e) {           // 业务校验不通过
          System.out.println("创建失败：" + e.getMessage());
      }

  什么时候"抛异常"、什么时候"返回 false"？（重要）
    情况不同：
      - 调用方【给错了数据】（金额传 -5、订单号重复）-> throw，
        因为这是不该发生的，要大声喊出来
      - 【正常可预期的业务结果】（订单不存在、已支付不能再付）-> return false
    口诀："是你给错了" -> 抛异常；"是正常结果" -> 返回 false

【2.6 null 与空指针（NPE）】
  错误写法： if (id.trim().isEmpty())       // id 是 null 时 -> NullPointerException，程序崩
  正确写法： if (id == null || id.trim().isEmpty())
  ★ 顺序是故意的！Java 的 || 是【从左到右、短路】的，
    id == null 为真时，右边不再执行，所以不会 NPE。

【2.7 可变 vs 不可变（设计原则）】
  "能不变就不变；非要变，也只开放必须变的那一小部分。"
  想要"金额可改"时，三种做法：
    1) 去掉 final + 加 public setAmount    -> 谁都能随时改，规则没地方拦
    2) 保留私有 + 提供带校验的 correctAmount（推荐）-> 能改，且必须过规则
    3) 干脆不改，作废这张、重开一张        -> 最干净，保留完整历史

三、集合：用 Map 当数据库
============================================================

【3.1 Map<K,V>】
  Map<String, Order> orders = new LinkedHashMap<>();
  键 = 订单号，值 = 订单对象。相当于一本字典：查"订单号" -> 得到那笔订单。

【3.2 为什么不用 List？】
  Map 能【按订单号一步查到】；List 要从头一个个翻。订单越多差距越大。

【3.3 LinkedHashMap 与 HashMap 的区别】
  LinkedHashMap 额外记住【插入顺序】，所以"查看全部"会按创建顺序显示，不乱七八糟。
  （数据库里的等价做法：加一个自增主键 seq，ORDER BY seq）

【3.4 常用方法】
  put(键, 值)          放进去
  get(键)              按键取，没有返回 null
  containsKey(键)      这个键在不在
  size()               里面有几个
  values()             取出所有"值"
  isEmpty()            （List/Map 都有）是不是空的

【3.5 put 的坑（重要）】
  Map 的 put：如果键已存在，会【直接把旧值覆盖掉】。
  所以没有"防重复"检查时，重复创建 = 静默丢数据（程序不报错，数据悄悄少了）。
  这就是 createOrder 里必须先 repository.contains(id) 的原因。

【3.6 防御性拷贝】
  错误： return orders.values();
        -> 给出去的是 Map 内部集合本身（视图），外部能 add/remove，
           等于把仓库钥匙给了别人，封装白做
  正确： return new ArrayList<>(orders.values());
        -> 复制一份新列表再给出去，别人怎么折腾都动不了你的数据


============================================================
四、业务层设计原则
============================================================

【4.1 依赖注入（DI）—— 后端最核心的思想之一】
  public OrderService(OrderRepository repository) {   // 从外面传进来
      this.repository = repository;
  }

  为什么不直接在 OrderService 里 new OrderRepository()？
    - 那样"用哪个仓库"就焊死在 OrderService 里了，换数据库必须回来改它
    - 从外面递进来，OrderService 只管用，换成什么仓库都不关心
    - 附带好处：测试时可以塞一个"假仓库"进去
  一句话：我需要的零件，你递给我，别让我自己造。

【4.2 校验要放在业务层】
  OrderRepository 只会傻乎乎地 put（存），
  "什么情况不许存"这种判断，只能由 OrderService 把关。

【4.3 卫语句（guard clause）】
  先把异常情况挡在最前面，剩下的代码就都是"正常路径"，不用嵌套。

    // 推荐
    if (order == null) throw ...;
    return order;

    // 等价但正常逻辑被挤进 else，逻辑长了读起来累
    if (order != null) return order; else throw ...;

【4.4 createOrder 的三道校验（顺序不能错）】
  1) 订单号不能为空   （先判 null，再判 trim 后是否为空 —— 顺序反了会 NPE）
  2) 金额必须大于 0
  3) 订单号不能重复   （用 repository.contains(id)）
  全通过后：new Order(id, amount, UNPAID) -> repository.add(order) -> return order

五、Maven 工程化
============================================================

【5.1 标准目录结构（全世界的 Java 项目都这样）】
  pom.xml                          项目说明书：依赖、编译版本、插件
  src/main/java/...                源码
  src/main/resources/
      application.properties       配置（数据库地址等）
      schema.sql                   建表脚本
  src/test/java/...                测试代码
  src/test/resources/
      application.properties       测试专用配置（用内存数据库）
  target/                          构建产物（不用管，也别提交到 Git）

【5.2 pom.xml 各部分的含义】
  <parent>       继承 Spring Boot 官方父 POM -> 依赖版本由它统一管理
  <groupId>      组织名，如 com.example
  <artifactId>   项目名，如 order-app
  <version>      版本号，如 1.0.0
  <properties>   java.version=21（父 POM 认这个属性决定编译版本）
  <dependencies> 依赖清单
  <scope>test</scope>     只在测试时用，不进最终程序
  <scope>runtime</scope>  编译时不用、运行时才需要（如数据库驱动）
  <build><plugins>  spring-boot-maven-plugin（提供 run 命令、打可执行 jar）

【5.3 常用命令】
  mvn compile              编译
  mvn test                 编译 + 跑测试
  mvn spring-boot:run      启动 Spring Boot 服务
  mvn package              打包成 jar
  mvn -q xxx               安静模式（少打日志）
  mvn -B xxx               批处理模式（日志更干净，适合脚本）

【5.4 中文乱码的两个处理】
  javac 源码编码：   javac -encoding UTF-8 ...
  Java 运行输出编码： java -Dstdout.encoding=UTF-8 -Dstdin.encoding=UTF-8 ...
  Maven 报错乱码：   编译前执行 $env:JAVA_TOOL_OPTIONS = "-Duser.language=en -Duser.country=US"

【5.5 怎么读编译报错】
  src\OrderRepository.java:19: error: cannot find symbol
      public ListAll<Order> getAll() {
             ^
    symbol:   class ListAll
  三段信息：哪个文件:第几行 -> 错误类型 -> ^ 箭头指着出问题的地方
  ★ 编译器不报错 != 代码写对了（编译器只认语法，不认你的意图）

六、单元测试（JUnit 5）
============================================================

【6.1 是什么、为什么要写】
  一段自动运行的代码，用来验证行为对不对。
  以前验证功能要手敲菜单，又慢又容易漏；现在改一行代码 -> mvn test -> 3 秒告诉你有没有弄坏。
  面试必问：它证明你写的不只是"能跑"，而是"能保证对"。

【6.2 三个核心】
  1) 测试方法带 @Test 注解（没它 JUnit 当这个方法是空气 —— 会白写）
  2) AAA 模式：Arrange 准备 -> Act 执行 -> Assert 断言
  3) @BeforeEach：每个测试方法执行前都先跑一次，保证测试之间互不干扰

【6.3 断言方法】
  assertEquals(期望值, 实际值)      两者相等吗（期望在前，别写反）
  assertTrue(x) / assertFalse(x)    真 / 假
  assertNull(x) / assertNotNull(x)  空 / 非空
  assertThrows(异常类.class, () -> { ... })   这段代码应该抛异常，否则测试失败

  () -> service.createOrder("A001", 0) 是 lambda：
  把这段代码包起来先不执行，交给 assertThrows 去执行。

【6.4 怎么读测试失败（很有价值）】
  org.opentest4j.AssertionFailedError: expected: <订单号已存在> but was: <订单号已存在：A001>
  expected = 你期望的；but was = 代码实际给出的。
  ★ 这不一定是"代码有 bug"，可能是"你的期望写得不够精确"。
    真实故事：测试发现错误信息其实带上了订单号（"订单号已存在：A001"），
    而人以为只有"订单号已存在" —— 测试帮你看清了真实行为。
  两种修法：
    A) assertEquals("订单号已存在：A001", e.getMessage());   期望写精确
    B) assertTrue(e.getMessage().contains("订单号已存在"));  只检查包含（更抗改动）

【6.5 测试文件的两条硬性规矩】
  1) 文件名必须以 Test 结尾（Maven 靠这个找测试）
  2) 必须放在 src/test/java 下（放错地方 = 不编译也不运行，一声不响）

【6.6 有了数据库之后，测试怎么写】
  @SpringBootTest                 启动 Spring 上下文（不再手动 new）
  @Autowired OrderService service;  让 Spring 把对象递进来
  @Autowired JdbcTemplate jdbc;
  @BeforeEach void setUp() { jdbc.update("DELETE FROM orders"); }   // 每个测试前清表
  测试代码本身（断言部分）几乎不用改 —— 这就是分层的好处。


============================================================
七、Spring Boot 与 Web 接口
============================================================

【7.1 注解是什么】
  注解本身什么都不干，它只是一张"贴纸"（元数据），作用是给框架留记号。
  就像行李箱上的"易碎品"标签：标签不保护箱子，是搬运工看到标签后改变了做法。
  一句话：注解 = 给框架看的贴纸。你贴标签表达意图，框架读标签干活。
  没有注解的年代，要用 XML 把关系一条条写出来，烦到出名。

【7.2 启动时发生了什么】
  1. JVM 执行 OrderAppApplication.main()
  2. 看到 @SpringBootApplication -> 开始扫描 com.example.order 包
  3. 读所有类身上的"贴纸"：
       发现 @Service     -> new OrderService()，放进对象池
       发现 @Repository  -> new OrderRepository()，放进对象池
       发现 @RestController -> 看构造方法需要 OrderService -> 从对象池捞出来塞进去（依赖注入）
       发现 @GetMapping / @PostMapping -> 记下路由表
  4. 启动 Tomcat，监听 8080
  5. 浏览器来请求 -> 查路由表 -> 调用对应方法 -> 返回 JSON

【7.3 注解分类速查】
  【身份】@SpringBootApplication  从这儿开始（自动配置 + 组件扫描）
          @Service               交给 Spring 管（业务层）
          @Repository            交给 Spring 管（数据层）
          @RestController        交给 Spring 管 + 处理 HTTP 请求
              （这几个功能本质一样，名字不同是为了表达角色）
  【路由】@RequestMapping("/orders")  贴在类上，公共前缀
          @GetMapping             处理 GET
          @PostMapping            处理 POST
          @GetMapping("/{id}")    花括号 = 路径占位符（变量，不是固定文字）
  【取数据】@PathVariable          从 URL 路径取值：/orders/A001 -> id="A001"
            @RequestBody           从请求体取 JSON，并自动转成 Java 对象
  【回复】  @ResponseStatus(HttpStatus.CREATED)  强制指定成功状态码（默认 200）
            返回对象 -> Spring 自动转 JSON
  【异常】  @RestControllerAdvice      全局兜底，所有 Controller 的异常都归我管
            @ExceptionHandler(异常类.class)  这类异常交给下面这个方法处理
  【测试】  @Test / @BeforeEach / @SpringBootTest / @Autowired

【7.4 完整地址怎么来的】
  @RequestMapping("/orders")   ← 类上前缀
  @GetMapping("/{id}")         ← 方法上后缀
  -------------------------------------------------
  合起来：GET /orders/{id}

【7.5 record（Java 16+）】
  record CreateOrderRequest(String id, int amount) { }
  "只装数据的类"，一行顶过去十几行（自动生成构造方法、getter、equals 等）。
  取值用 request.id()、request.amount()（注意是 id() 不是 getId()）。

【7.6 JSON 是怎么来的（为什么 getter 很重要）】
  返回 Order 对象，Spring 用 Jackson 自动序列化成：
    {"id":"A001","amount":100,"status":"UNPAID"}
  Jackson 靠 getter 取名字：getAmount() -> JSON 里的 amount。
  发过来的 JSON 也要靠字段名匹配：字段名必须和 JSON 的 key 一致，否则塞不进去。

【7.7 把 Java 异常翻译成 HTTP】
  ApiExceptionHandler 接住 OrderService 抛的 IllegalArgumentException：
    返回 HTTP 400 + {"error":"金额必须大于 0"}
  对比控制台版的 try/catch + println —— 同一件事，两种表达方式。
  Web 版把它变成了全局的、写一次管所有接口。

【7.8 ResponseStatusException 还是 ResponseEntity？】
  两种等价写法：
    A) throw new ResponseStatusException(HttpStatus.NOT_FOUND, "订单不存在：" + id);
       方法返回类型干净（就是 Order）；错误靠"抛"。适合错误是少数情况。
    B) public ResponseEntity<Order> getOne(...) {
           if (order == null) return ResponseEntity.notFound().build();
           return ResponseEntity.ok(order);
       }
       返回类型里就带着状态码，一目了然。适合一个方法要返回多种状态码。
  团队统一用一种就行，别混着用。

【7.9 为什么"查不到"不能直接 return null（大坑）】
  public Order getOne(@PathVariable String id) {
      return service.findOrder(id);      // 查不到时返回 null
  }
  结果：HTTP 200 + 空响应体。客户端以为"成功了，订单就是这个（空的）"——【假成功】。
  原则：错误必须"响亮"地表达出来（404 + 错误信息），不能悄悄返回空值让调用方猜。

【7.10 Swagger UI（springdoc-openapi，零代码生成接口文档）】
  依赖：org.springdoc:springdoc-openapi-starter-webmvc-ui
  自动扫描 @RestController，生成可视化页面，点按钮就能调接口。
  地址：
    /swagger-ui.html     人类看的图形界面
    /v3/api-docs         机器看的 JSON（Postman 能一键导入）
  用法：展开接口 -> Try it out -> 填参数/请求体 -> Execute -> 看 Server response


============================================================
八、持久化：从内存到数据库
============================================================

【8.1 为什么必须做】
  内存 Map 的致命问题：服务一重启，数据全没了。
  真实业务（订单、用户、支付）必须持久化，否则毫无意义。

【8.2 选型：H2 文件模式】
  - H2 是纯 Java 的内嵌数据库，加个依赖就能用，不用单独安装
  - 文件模式：数据存在项目下的 data\orderdb.mv.db 文件里，重启不丢
  - 想换成 MySQL 只要改 application.properties 的 url/driver/用户名密码
  依赖：
    spring-boot-starter-jdbc        提供 JdbcTemplate + HikariCP 连接池
    com.h2database:h2 (runtime)     数据库驱动

【8.3 关键配置 application.properties】
  spring.datasource.url=jdbc:h2:file:./data/orderdb    文件模式
  spring.datasource.driver-class-name=org.h2.Driver
  spring.datasource.username=sa
  spring.datasource.password=
  spring.sql.init.mode=always           每次启动都执行 schema.sql
  spring.h2.console.enabled=true        打开 /h2-console 数据库控制台
  测试专用 src/test/resources/application.properties：
    spring.datasource.url=jdbc:h2:mem:testdb    内存模式，跑完就消失，不污染真实数据

【8.4 建表脚本 schema.sql】
  CREATE TABLE IF NOT EXISTS orders (
      seq    BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 自增序号，保持插入顺序（等价 LinkedHashMap）
      id     VARCHAR(64) NOT NULL UNIQUE,        -- 订单号，唯一约束（数据库再兜一层底）
      amount INT         NOT NULL,               -- 金额
      status VARCHAR(16) NOT NULL                -- 状态，存枚举的 name()
  );
  IF NOT EXISTS 保证脚本可重复执行（每次启动都会跑）。

【8.5 JdbcTemplate 常用方法】
  jdbc.update("INSERT INTO orders (id, amount, status) VALUES (?, ?, ?)", a, b, c);
      执行增删改；? 是占位符，后面的参数按顺序填进去（防 SQL 注入）
  jdbc.query("SELECT ... WHERE id = ?", RowMapper, id);
      查询，每一行交给 RowMapper 变成 Java 对象，返回 List
  jdbc.queryForObject("SELECT COUNT(*) FROM orders WHERE id = ?", Integer.class, id);
      查询单个值

【8.6 RowMapper：把一行数据库记录变回对象】
  private static final RowMapper<Order> TO_ORDER = (rs, rowNum) -> new Order(
          rs.getString("id"),
          rs.getInt("amount"),
          OrderStatus.valueOf(rs.getString("status"))
  );
  rs = ResultSet（结果集），rs.getString("列名") 按列名取值。

【8.7 SQL 基础速查】
  SELECT 列1, 列2 FROM 表 WHERE 条件 ORDER BY 列
  INSERT INTO 表 (列...) VALUES (值...)
  UPDATE 表 SET 列 = 值 WHERE 条件      ★ 忘了 WHERE 会改全表
  SELECT COUNT(*) FROM 表 WHERE 条件   数一数有几行
  AUTO_INCREMENT 自增主键；UNIQUE 唯一约束

【8.8 ★★ 最重要的观念变化：内存"共享对象" vs 数据库"必须写回"】

  内存版（旧）：
      Order order = repository.get(id);     // 拿到的是 Map 里【同一个对象】
      order.setStatus(PAID);                // 改它 = 直接改了 Map 里的对象，自动生效
      return true;                          // 不用保存

  数据库版（新）：
      Order order = repository.get(id);     // 拿到的是【新造的对象】，数据库里那份没变
      order.setStatus(PAID);                // 只改了内存里的这个副本
      repository.update(order);             // ★ 必须显式写回数据库（UPDATE）
      return true;

  一句话：内存靠"对象引用共享"自动同步；数据库必须【显式保存】。
  漏了 update(...) 的后果：接口返回"支付成功"，但重启后状态还是 UNPAID（假成功）。

【8.9 换数据库只改了一个文件（分层的价值）】
  改动清单：
    pom.xml                  加 jdbc + h2 依赖
    src/main/resources/      加 application.properties、schema.sql
    OrderRepository.java     重写方法体（Map -> SQL）
    OrderService.java        pay / cancel 各加一句 repository.update(order)
    OrderServiceTest.java    改成 @SpringBootTest + 清表
  没动：Main.java、OrderController.java、Order.java、OrderStatus.java、ApiExceptionHandler.java

九、HTTP 状态码速查
============================================================

  200 OK            正常返回
  201 Created       创建成功（POST /orders）
  400 Bad Request   参数不合法（订单号空、金额<=0、订单号重复）—— ApiExceptionHandler 自动处理
  404 Not Found     资源不存在（查不到这个订单）
  409 Conflict      状态冲突（已支付的订单又想支付/取消）
  500 Internal Server Error  服务器自己出了 bug（比如空指针）

  为什么 404 不是 400？
    400 = 你的请求（参数）有毛病
    404 = 你要的东西不存在
    409 = 东西在，但现在这个状态不允许你这么干

十一、常见坑清单
============================================================

【1】端口被占用
  现象：启动时 Process terminated with exit code: 1
  根因：往上看几行，会有一句 "Web server failed to start. Port 8080 was already in use."
        （最下面那堆 [ERROR] ... Help 1 是模板废话，根因在上面）
  原因：已经有一个服务在跑了（常见于自己启动了两次）
  解决：Ctrl+C 停掉旧的，或查 PID 杀进程，或换端口：
        mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8081

【2】改完代码接口还是老样子 / 404
  原因：Spring Boot 默认不热重载
  解决：Ctrl+C 后重新 mvn spring-boot:run

【3】浏览器"拒绝连接"
  原因：服务没在跑（不是代码问题）
  解决：先启动服务；用 curl 确认返回 200

【4】终端看起来"卡住了"
  现象：打完 "Started ... in x seconds" 就不动了，没有提示符
  真相：那是【服务器在正常运行】，常驻进程就该这样
  判断：另开终端 curl 一下，200 就是活着
  干活：另开一个终端（VS Code：Ctrl+Shift+`），一个跑服务、一个敲命令

【5】数据重启后全没了
  原因：数据存在内存 Map 里
  解决：做持久化（见第八节）

【6】测试放了没跑，还不报错
  原因：测试文件不在 src/test/java 下
  现象：mvn test 只显示 Nothing to compile - all classes are up to date
  解决：挪到正确目录

【7】测试方法写了但没执行
  原因：忘了 @Test 注解（没它 JUnit 当它不存在）

【8】HTTP 200 + 空响应体（假成功）
  原因：查不到时直接 return null
  解决：抛 ResponseStatusException(NOT_FOUND)

【9】数据库版忘了写回
  原因：pay/cancel 改完内存对象就 return 了，没调 repository.update()
  后果：接口说"成功"，重启一看状态没变

【10】中文乱码
  编译：javac -encoding UTF-8
  运行：-Dstdout.encoding=UTF-8 -Dstdin.encoding=UTF-8
  Maven 报错英文：$env:JAVA_TOOL_OPTIONS = "-Duser.language=en -Duser.country=US"

十二、面试问答速查
============================================================

Q1 介绍下你的架构？
   四层：界面层（Main / OrderController）、业务层（OrderService）、
   数据层（OrderRepository）、实体（Order / OrderStatus）。
   关键点：界面层里一个业务判断都没有，规则全在 Service —— 改规则只动一个地方。
   依赖方向单向：界面 -> 业务 -> 数据 -> 实体。

Q2 为什么订单号加 final？
   它是订单的"身份"，而且（内存版）是 Map 的 key。
   key 一变，Map 里存的键和对象里的订单号就对不上，数据自相矛盾。
   （数据库版同理：id 是 UNIQUE 主键，不允许改）

Q3 为什么创建订单抛异常、支付失败返回 false？
   创建失败是"调用方给错了数据"（不该发生）-> 抛异常逼它改；
   支付失败是"正常可预期的业务结果"（订单不存在/已支付）-> 返回 false 让调用方处理。

Q4 怎么保证订单号不重复？
   先在业务层 contains(id) 检查，重复就抛异常；
   数据库层再加 UNIQUE 唯一约束兜底。
   内存版不检查的后果：Map 的 put 会静默覆盖旧订单 —— 不报错，数据悄悄丢。

Q5 为什么用 Map / 为什么选 LinkedHashMap？
   Map 按订单号一步定位，List 要遍历。
   LinkedHashMap 记住插入顺序，让"查看全部"不乱序。
   （数据库版用自增 seq + ORDER BY seq 达到同样效果）

Q6 以后要换数据库，改哪些代码？
   只改 OrderRepository（外加配置文件和依赖）。
   因为 Service 持有的仓库是外面递进来的（依赖注入），它不关心仓库是内存、文件还是 MySQL。
   ★ 这个我们已经实测过：从内存 Map 换到 H2 数据库，Main / Controller / Order / OrderStatus 一行没改。

Q7 你怎么保证代码是对的？
   写了 6 个 JUnit 测试：正常创建、金额非法、订单号重复、订单号为空、支付成功、支付不存在的订单。
   而且测试真的抓到过问题：我以为重复创建的报错是"订单号已存在"，
   实际代码里带上了订单号"订单号已存在：A001"——
   这说明测试能帮你发现"你以为的行为"和"真实行为"的差异。

Q8 内存版和数据库版，修改状态有什么不同？
   内存版：get 拿到的是同一个对象引用，setStatus 直接生效；
   数据库版：get 出来的是一个副本，改完必须调 update() 显式写回数据库，
             否则数据不会变（或重启后丢失）。

Q9 REST 风格的状态码怎么选？
   200 正常 / 201 创建成功 / 400 参数不合法 / 404 资源不存在 / 409 状态冲突 / 500 服务器 bug。
   语义要分清：400 是"你请求有毛病"，404 是"东西不存在"，409 是"状态不允许"。

Q10 什么是依赖注入？
   对象需要的依赖，不由它自己 new，而是从外面传进来（构造方法参数）。
   好处：解耦（换实现不用改代码）、可测试（能塞假对象）、
         在 Spring 里由容器统一创建和组装。

十三、并发安全（"先查后改"陷阱）
============================================================

【13.1 问题：先查后改有时间窗口】

  危险写法：
      Order order = repository.get(id);                    // ① 查
      if (order.getStatus() != UNPAID) return false;       // ② 判断（在 Java 里）
      order.setStatus(PAID);
      repository.update(order);                            // ③ 改

  ① 和 ③ 是两条独立 SQL，中间隔着一段时间。这段时间里数据库可能已被别人改过。

  两个请求同时支付同一笔订单：
      请求A: 查到 UNPAID
      请求B:              查到 UNPAID
      请求A: 判断通过 -> 改成 PAID -> 保存 -> 返回"成功"
      请求B:                          判断也通过 -> 改成 PAID -> 保存 -> 返回"成功"
    结果：同一笔订单被"支付成功"两次。

  ★ 实测（20 线程并发支付同一订单，用旧的"先查后改"写法）：
      成功次数 = 17 次！   （不是 1 次）
    这种 bug 平时测试很容易漏掉，因为它是"时序相关"的 ——
    两个请求错开一点点就没事，上线半年可能都不出现，一出现就是资金问题。

【13.2 修复：把判断条件写进 SQL 的 WHERE】

  "检查"放在哪里，决定了它安不安全：

      放在 Java 里（if 判断）  -> ❌ 检查和修改之间有窗口期
      放在 SQL 的 WHERE 里     -> ✅ 检查和修改在同一个原子操作内

  修复后的 SQL：
      -- 修改前：无条件改
      UPDATE orders SET status = ? WHERE id = ?

      -- 修改后：改的时候顺便检查状态
      UPDATE orders SET status = ? WHERE id = ? AND status = 'UNPAID'

  数据库执行单条 SQL 是【原子】的 —— 要么全部生效，要么完全不生效，不会被插队。
  两个请求必然排队：先到的改成功（rows=1），后到的发现条件不满足（rows=0）。

【13.3 靠"受影响行数"判断成败】

  jdbc.update(...) 返回被修改的行数：

      int rows = jdbc.update(
              "UPDATE orders SET status = ? WHERE id = ? AND status = ?",
              newStatus.name(), id, OrderStatus.UNPAID.name());
      return rows == 1;

      rows == 1  -> 我改到了，说明订单存在且当时还是 UNPAID -> 我抢到了，成功
      rows == 0  -> 一行都没改到 -> 订单不存在，或已被别人改了 -> 失败

  好处：不需要额外查询、不需要加锁、不需要 synchronized，
        一条 SQL 同时完成"检查 + 修改 + 判断结果"。

【13.4 Service 层随之简化】

  修复前（11 行，且 pay / cancel 几乎重复）：
      public boolean pay(String id) {
          Order order = repository.get(id);
          if (order == null) return false;
          if (order.getStatus() != OrderStatus.UNPAID) return false;
          order.setStatus(OrderStatus.PAID);
          repository.update(order);
          return true;
      }

  修复后（1 行，pay / cancel 共用同一个数据层方法）：
      public boolean pay(String id) {
          return repository.updateStatusIfUnpaid(id, OrderStatus.PAID);
      }

      public boolean cancel(String id) {
          return repository.updateStatusIfUnpaid(id, OrderStatus.CANCELLED);
      }

  原来的三件事（查存在、查状态、改状态）合并成一条 SQL。
  附带好处：少一次查询、消除重复代码。

【13.5 同一模式的通用场景（面试加分）】

  凡是"检查某个条件，然后基于该条件做修改"都要考虑并发，写法都一样：

      扣库存（不会超卖）：
          UPDATE product SET stock = stock - 1 WHERE id = ? AND stock > 0

      转账扣款（余额不足就扣不动）：
          UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?

      领优惠券 / 抢红包：同理，把"还有余量"写进 WHERE

【13.6 怎么测并发（CountDownLatch 发令枪）】

  关键：要让线程【同时】冲，而不是依次调用。用 CountDownLatch 当发令枪：

      CountDownLatch startGate = new CountDownLatch(1);   // 发令枪
      // 所有线程先 startGate.await() 集合等待
      // 主线程 startGate.countDown() 一声令下，20 个线程同时冲
      assertEquals(1, successCount.get());                // 只能有 1 个成功

  注意点：
      - 计数要用 AtomicInteger（普通 int++ 不是线程安全的）
      - 断言"恰好 1 个成功"，而不是"至少 1 个"—— 后者测不出重复支付

  实测（修复后，20 线程并发支付）：
      单元测试：Tests run: 8, Failures: 0
      HTTP 端到端：HTTP 200 出现 1 次，HTTP 409 出现 19 次  ✅

【13.7 什么时候需要事务 @Transactional】

  事务 = 一组操作"要么全成功，要么全失败"（ACID 里的 A：原子性）。
  Spring 的 @Transactional：方法内抛异常 -> 自动回滚。

  什么时候需要？
      当一次业务操作包含【多条】写操作时。
      例如：支付 = 改订单状态 + 插支付流水 + 更新统计表
            如果第 2 步失败，没有事务就会留下"订单已支付但没有流水"的脏数据。

      反之：只有一条写操作时，单条 SQL 本身就是原子的，不需要显式事务。

  ★ 能答出"什么时候不需要事务"，比只会说"我会加 @Transactional"更显成熟。
